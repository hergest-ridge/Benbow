# Sync and API

Single owner, several devices, server on LAN, often unreachable. Goal: offline-first clients, never lose data (data-safety S4, S5, S8, S11), simple to debug.

## Why not a CRDT
Conflicts are rare with one human. CRDTs (Automerge, Loro, Yjs) add opaque binary state, bindings that aren't mature on every KMP target, and harder export and debugging. An append-only revision DAG + 3-way merge gives the same "never lose" guarantee with plain, inspectable data. We can revisit this for real-time co-editing, which is a non-goal.

## Client local state
Implemented in `shared/client` (SQLDelight `BenbowDb`, `Benbow.sq`):
- `entry`: mirror of server entries (head revision id + body, LWW fields as JSON, conflict heads).
- `draft (entry_id, body, base_rev)`: in-progress editor text, autosaved. Not synced. The base is fixed when the draft starts, so the revision made from it has the right parent.
- `outbox (seq, op_id, entry_id, op, state pending|rejected, last_error)`: ordered ops as JSON. Acknowledged ops are removed; rejected ops stay for the user (never dropped silently).
- `kv`: connection (url, fingerprint, token, store id, epoch, device id), pull cursor, persisted HLC.
- A local write = cache update + outbox insert in one transaction (`JournalRepository`).
- `SyncEngine.sync()`: checks `/info` (store id, protocol) first, pushes in batches of 200, then pulls pages in transactions. Pull skips entries with pending ops (pending wins until acknowledged) and never touches drafts.
- Trash is the LWW field `deleted = "true"`; restore clears it.
- `attachment_ref` (as built 7.18 M1, ADR-041; `8.sqm`): one row per attachment link (entry, attachment, sha256, kind, mime, size, name, width, height, duration, captured_at, preview, caption, position, present, purged, changed_at: the link's clock's wall time, when it was taken off), made from `entry.attachments` by SQLite triggers on `entry` (insert, an update that changes `attachments`, delete), so every write path keeps it in step in the same statement; the migration fills it once from what the device holds. A value the triggers can't read (not JSON, a link without a file) gives no row and never fails the write. The entry's day, space and trash are joined from `entry`, never copied. The library, the trash's media and the device's estimates read it, never parsing JSON per row. Regenerable, not client-owned data. Tests: `AttachmentRefTest` (writes, a pull, unreadable values, agreement with `MediaRefs`), `MigrationTest` (the fill, a migrated file's schema equals a new one's).

## Revisions from drafts
A draft becomes a revision on: editor close, app backgrounded, 30 s idle, or every 2 min of continuous typing. Op: `entry.revision.put {entry_id, rev_id, parents:[base_rev_id], title, body, body_v, body_sha256}` (body = canonical Document JSON).

## Op types (v1)
`entry.create`, `entry.meta.set {field, value, hlc}` (day, kind, favorite, pinned, mood, appearance, space),
`entry.revision.put`, `entry.delete` / `entry.restore {hlc}`, `entry.tag.set {tag_id, present, hlc}`,
`entry.attachment.set {attachment_id, position, caption, present, hlc}`, `reaction.set {emoji, present, hlc}`,
`tag.upsert`, `tag_category.upsert`, `attachment.register`, `template.*`, `reminder.*`. Calendar events have their own store and ops (see "Calendar store" below, ADR-027).
Implemented: `entry.create`, `entry.revision.put`, `entry.meta.set` (protocol 1); `entry.attachment.put {attachment: meta, position, caption, present, hlc}` (protocol 2, replaces the planned `attachment.register` + `entry.attachment.set`: the immutable file meta travels with every link change, so a link is self-contained). Trash is `entry.meta.set deleted`. Favorite, mood, tags, reactions and a comment's parent are namespaced fields too (ADR-021): `favorite`, `pinned`, `mood`, `tag:<id>` = the name it was put on with (ADR-032: the id of a tag from before is its lowercase name; names live in the tag registry), `reaction:<emoji>`, `parent`. Protocol 3 (ADR-040, server 0.11.0): the field `space` (`board`: a note on the board, which the journal never shows) and the board's fields (`board_rank`, `board_pin`, `board_archived`); the server and clients speak 3 only, so an app that would show board notes in its journal stops syncing and asks to be updated (its outbox waits). The look of a note (ADR-047, 7.20 L1) is plain fields, `look_<layer>` = a token, within protocol 3: an older app keeps them as it keeps any field and draws the note in its color only.
`AttachmentState.purged` (ADR-041; additive, protocol 3 stays, never encoded while false): read by `MediaRefs` and `attachment_ref` since 7.18 M1, set only by the server's purge since M5 (`Purging` in shared/core); an entry deleted for good has the field `purged` = `true`, which no device may write (absorbed), and every link put on it is purged from the start; a purged link absorbs every later `entry.attachment.put` of it (applied, nothing changes) and carries `present = false` for older apps.
Metadata fields use per-field LWW ordered by a **Hybrid Logical Clock** (`hlc` = wall ms + counter + device id), so it tolerates phone clock drift.

## Push
`POST /api/v1/sync/push {protocol, device_id, ops:[...]}`. Ops are applied in order. Each op runs in its own transaction and is deduplicated by `op_id`.
Per-op result: `applied | duplicate | merged | conflict | rejected(reason)`. `rejected` stays in the client's "needs attention" list (S5).

## Revision conflicts (server)
When `parents[0] != head`:
1. Store the incoming revision anyway (DAG sibling). It is never lost.
2. Try a diff3 merge (base = parent, ours = head, theirs = incoming) over the canonical serialization, where one line = one block (content-format.md), using the shared code in `shared/core`. Then validate: the result must decode, and `_key`s must be unique (a duplicate counts as a conflict). As built (7.17 K4, ADR-040): a run of blocks both sides changed that holds the same blocks on all three (by `_key`, in order) merges block by block, and a list box's `checked` merges apart from the rest of its block, so ticks on neighbouring boxes from two devices, or a tick on one side and new words on the other, are no conflict; the same words changed two ways still are (`mergeAlike` in `Merge.kt`).
3. Clean merge → new merge revision with two parents, result `merged`.
4. Overlapping changes → entry gets `conflict_heads=[head, incoming]`, result `conflict`. Clients show a banner with both versions side by side. The user's resolution becomes a revision whose parents are both heads.

## Pull
`GET /api/v1/sync/pull?cursor=N&limit=500` → `{changes:[entity snapshots], next_cursor, has_more}`.
- `change_log.seq` is assigned inside the write transaction. SQLite's single writer means no gaps or reordering.
- Snapshots carry full current state + head body. Older revisions are fetched on demand (`GET /api/v1/entries/{id}/revisions`).
- Client rule: an entity with pending outbox ops keeps its local optimistic state until the push result arrives, then re-pulls. The server is the arbiter.
- Bootstrap a new device = pull from cursor 0 (heads only). Attachments load lazily.
- Live updates (Phase 2+): `GET /api/v1/sync/events` (SSE or WebSocket) announces new `seq`, which triggers a pull.

## Store identity (S11)
`GET /api/v1/info` → `{server_version, protocol_min, protocol_max, store_id, epoch, schema_version}`.
- Different `store_id` → the client refuses to sync and asks the user (new server? re-pair, keep local cache).
- `epoch` increased (server restored from backup) → client runs reconciliation: it sends the IDs and revision IDs it knows, the server answers with what it lacks, and the client re-pushes those. This is how device caches heal a restored server.
- Server cursor lower than client cursor without an epoch change → treat as a restore and reconcile.
- Implemented (server 0.3.0): `info.cursor`, `POST /api/v1/sync/reconcile {entries:[{id, head}]}` → `{missing_entries, missing_revisions}`. The client then pushes `entry.create` for missing entries, its head revision without parents for missing heads (if the server has an older head, both are kept as a conflict; heads still in the outbox go with their real parents) and every field value with its original HLC (stored locally in `entry.field_clocks`), then resets the cursor to 0 for a full pull. Restores bump the epoch past every epoch the data folder has seen (`--restore`, or the startup high-water check for hand-copied files).

## Calendar store (ADR-027, as built 7.3a, server 0.6.0)
Calendars and events sync on their own channel, beside the journal, and never through `entry` ops. Code: `app.benbow.core.calendar` (ops, `CalendarRules`), server `app.benbow.server.calendar`, client `app.benbow.client.calendar`.
- Op `{opId, kind: "calendar"|"event", id, fields:{name: value|null}, hlc}` (`CalendarOp`). Every field in the op takes that HLC and wins per field by LWW; a record exists from its first put (no create op), so an import is one op per event. Delete = `deleted = "true"` (trash), restore clears it. Idempotent by `opId` (the calendar's own `applied_ops`). An unknown kind, an empty id or no fields is `rejected`.
- `POST /api/v1/calendar/push {protocol, ops}` (calendar protocol 1, at most 500 ops, one transaction per op; another protocol answers 409) returns a `PushResponse`. `GET /api/v1/calendar/pull?cursor=&limit=` (at most 500) returns `{changes:[{kind, id, fields:{name:{value, hlc}}}], nextCursor, hasMore}` from the calendar's own change log. A put is logged even when every field lost, so a device that skipped the record while its op was pending pulls the winner. Results: `applied | duplicate | rejected(reason)`; there are no merges or conflicts. Without a calendar store (its file didn't open) both answer 503 `no_calendar` and the journal works as usual.
- `GET /api/v1/info` gains `calendar: {protocol, epoch, cursor}` (additive in v1; absent on older servers and when the calendar file didn't open). Against such a server calendar ops wait in the outbox (`Unsupported`, shown on the server screen).
- Client: `calendar.db` (its own SQLDelight database `CalendarDb`) holds calendars, events (with `calendar`, `title`, `start`, `start_day`, `end_day`, `deleted` derived from their fields), its own outbox, cursor, epoch, store id and HLC. `AppServices.syncAll` runs the journal first and the calendar (`CalendarSync`) only after the journal's sync succeeded; its result is kept apart (`calendarStatus`) and never fails the journal's. Pending and rejected calendar ops count in the sync status; rejected ones are listed and retried with the journal's.
- The cache belongs to one store: another store id stops it (`WrongServer`). Unpairing waits for the calendar's outbox too, then clears it.
- Restore: the calendar file has its own epoch. A new calendar epoch (or a server cursor below the device's) makes the client re-push every field value it has with its original HLC (one op per record and HLC; LWW makes that safe), then pull from 0. No revision reconciliation is needed.
- Tests: `CalendarSimulation` (shared/testing) against the in-memory and the SQLite store; `CalendarClientTest` (two devices, lost responses, an older server, restore, another store, moving 5.1 events); `CalendarApiTest`; `CalendarStoreTest` (files, snapshots, restore).
- Trackers (ADR-050, 7.21; the server side as built B2): the kinds `tracker`, `column`, `cell` and `span` (data-model.md "Trackers") go over this channel with the same ops, rules and protocol 1. `calendar` in `/info` gains `kinds` (additive): an app sends tracker ops only to a server that lists them; against an older server they wait in the outbox (`Unsupported` for trackers, shown on the server screen) while the calendar's go on. An older app keeps none of a kind it doesn't know (as now), so the `calendar.db` migration that adds the tracker tables resets the cursor to 0 and the next sync pulls every record again (LWW makes that safe). As built B3: `CalendarSync` pushes only the pending ops of the kinds `/info` names (`pendingOpsOf`; no kinds = calendars and events), re-pushes trackers' records too after a restore, and reports what waits as `Done.held`, which the server screen shows («Сервер пока без трекеров…»). A cell's id is `<column id>:<day>`, so two devices marking one day write one record; counts are per-device fields. The server's `CalendarRules` append to `field_history` every value a put overwrites and every value that loses (one code path for every kind); it is the server's alone, never pulled, and kept in snapshots and the off-site copy.

## Blobs (attachments)
1. Client copies the media to private storage, computes SHA-256, creates the attachment row (`local`) and links it to the entry. The entry can sync before the blob arrives.
2. Upload (WorkManager on Android, resumable, tus-like):
   `HEAD /api/v1/blobs/{sha256}` (already exists? done) → `POST /api/v1/uploads {sha256,size,mime}` → `PATCH /api/v1/uploads/{id}` with `Upload-Offset`, 4–8 MB chunks → server verifies (S7) → `uploaded`.
3. Download: `GET /api/v1/blobs/{sha256}` with HTTP Range (video streaming). Previews: `/thumb?w=`. The client generates its own preview at capture time (images and video frames) and uploads it, so the server doesn't need ffmpeg early on.
4. Client cache policy: LRU by size cap + max age, favorites pinned offline. Settings are configurable (P1). Start weak (thumbnails + recent items).
   Implemented (3.4, `MediaStore.evict`, after each sync): large files (≥ 1 MB) are kept under a cap (phone 2 GB, desktop 10 GB), least recently viewed first; only downloads and captured files the server confirmed more than 7 days ago may go (its backup job has copied them by then); previews always stay. Thumbnails of files not yet on the server carry an amber dot. Later: stream video with Range instead of downloading it whole, pin favorites offline.
6. Implemented on the client (3.2, `MediaStore`): files live in the app's media folder named by SHA-256 (table `media`, origin `captured` or `downloaded`). Import = copy + hash + fsync + atomic rename, then `JournalRepository.attach` records the file, queues `entry.attachment.put` and shows it at once, in one transaction. Uploads run after each successful text sync (8 MB chunks, resume from the server's offset, restart once on a checksum mismatch); a captured file is marked uploaded only after the server verified it. A file that fails doesn't hold back the rest of the queue (`uploadEach`): the next ones go, the first failure is reported and retried with the next sync, and three failures in a row stop the round. Timeouts: connect 5 s, silence on a connection 30 s, a request 30 s except a chunk (5 min). Downloads are verified by hash before they are kept. When a file is placed, the server logs a change for the entries that point at it, so devices and the Markdown export (relative links) learn it's there.
5. Implemented on the server (3.1, `BlobStore`): bytes are content-addressed by SHA-256 (`blobs` table); attachment metadata is separate (3.2). `HEAD|GET /api/v1/blobs/{sha256}` (Range, `ETag`, immutable caching) · `POST /api/v1/uploads {sha256,size,mime,name?,captured_at?}` → `{id|null, offset, complete}` (null id = already there; an open upload of the same file is resumed) · `PATCH /api/v1/uploads/{id}` + `Upload-Offset`, ≤16 MB per chunk, 409 with the right offset on mismatch, 422 when the finished file doesn't match its hash (upload dropped, start over), 507 when the disk lacks size + 1 GB, 503 `media_unavailable` while the media folder is gone or isn't this store's (ADR-042; also for a known file's download and for purge preview and commit; devices keep their files and try again later). A chunk is read whole into memory before its upload is locked and written (`ChunkBody`), so a connection that dies mid-chunk can't hold the upload: one cut short of its Content-Length answers 400 `incomplete`, one silent for 30 s 408 `stalled`, and nothing of either is written (server 0.8.5; before, a phone's socket reset mid-chunk held its upload until the server restarted, `UploadCutOffTest`).

7. Link card pictures (7.15, ADR-038) are blobs with no attachment, like previews: the device that read the page keeps the JPEG (`JournalRepository.keepFile`, uploaded with the rest), the block names its SHA-256, other devices fetch it by hash. The web client asks its server to read the page (`POST /api/v1/links/preview {url}` → `{url, title?, description?, site?, image?, width?, height?, mime?}`; an address that is a picture comes back as that picture, kept as the site gave it, with its type and size, and the browser fetches it by hash and attaches it under the link (ADR-045); public addresses only, 512 KB of HTML, 5 s, 5 redirects; 400 `bad_url`, 502 `no_page`), and the server stores the picture as a blob itself.

8. 7.18, ADR-041 (rules in data-safety.md "Purge"). As built (M4, server 0.11.3): `GET /api/v1/storage` → `StorageReport {files, bytes, kinds, states, months:[{month, kinds}], disk, mirror, database, snapshots, counted}`: each file once, as the most alive of its holders (`StorageCount` over `MediaRefs`: kinds `video`, `image`, `sound` (audio and voice), `drawing`, `file`, `preview` (previews and link pictures); states `live`, `trash`, `removed`, `unreferenced`), its month the holding entry's day; the count is kept until the change-log cursor or the blobs move, the disks (`FileStore` of the media folder and of `backup.mirror`), the DB file and `backups/db` are read at each ask; 503 `no_media` without a blob store. The client keeps the last report with its store id (`storage.report` in kv) for when the server is away. Planned (M5): the quarantine with its days in the report. As built (M5, server 0.12.0): `POST /api/v1/purge/preview PurgeRequest {entries, attachments:[{entryId, attachmentId}], unreferenced}` → `PurgePreview {planId, entries, links, files:[{sha256, size, kind, name}], bytes, staying:[{sha256, size, entries, live}], notArrived, freesOn}` (a plan lives ten minutes, kept by the server); `POST /api/v1/purge/commit {planId}` → `PurgeDone {purgeId, bytes, freesOn}`, or 409 `changed` (the device previews again), 410 `expired`, 400 `not_in_trash` / `referenced`; 503 `no_purge` without a blob store. `StorageReport` gains `waiting` and `waitingUntil` (the quarantine). An upload of a file whose every link is purged answers 410 `purged`. As built (M6): `GET /api/v1/storage/unreferenced` → `[UnreferencedFile {sha256, size, mime, path, since}]`, files no entry references placed 30 days ago or more, the heaviest first; `PurgeRequest.unreferenced` naming a younger one answers 400 `too_new`. The undo and «Освободить сейчас» are the admin page's only (`/admin/purges/{id}/undo`, `/free`).

## Sync triggers
App start and foreground, connectivity change, local change (debounced 2 s), periodic WorkManager (15 min, network required), manual pull-to-refresh. Exponential backoff with jitter.
Implemented (`SyncController`): request (start/foreground, pull-to-refresh, after pairing), local change after 2 s, every 2 min while in the foreground, backoff 5 s → 5 min with ±20% jitter. Android: default-network callback (back online → sync), WorkManager periodic sync (15 min, network required) and a one-off sync 5 s after leaving the app, which also survives the process being killed.

## Pairing and security
- Manual: enter `host:port` in the app plus a one-time 6-digit code shown on the admin page (TTL 5 min, single use, burned after 5 wrong guesses). The admin page with codes and devices is served **only to the server PC itself** (loopback), and admin POSTs must be same-origin (CSRF).
- QR: admin page shows `benbow://pair?h=<host>&p=<port>&c=<code>&fp=<cert sha256>`.
- `POST /api/v1/pair {code, device_name, platform}` → long-lived device token (stored hashed on the server, in Keystore-backed storage on Android). `Authorization: Bearer <token>`. Devices can be revoked on the admin page.
- Transport (ADR-012): HTTPS only. The server generates a self-signed certificate on first run. Clients pin its SHA-256 fingerprint from pairing (QR `fp` or shown next to the manual code) and reject any other certificate. A certificate rotation flow re-pairs or confirms the new fingerprint on the admin page.
- Browser (ADR-029, W2): the web client is served by the server at `/app/` and pairs only with that origin (`Pairing.probeOrigin`): no address to type, no fingerprint to compare or pin, since the browser itself has judged the certificate (a one-time warning for the self-signed one) and its fetch can't read it. The user enters only the code; the connection stores an empty fingerprint. The token lives in the page's own database (IndexedDB of that origin). A different address (IP vs host name) is a different origin, so a separate browser device with its own copy.
- Outside the LAN: a VPN of the owner's choice. Tailscale's own servers have refused Russian addresses since 2024 (ADR-039).

## Letters between servers (ADR-039, F1 as built, server 0.10.0)
Friends' servers talk only in sealed letters (`app.benbow.server.peer`); devices know nothing of it yet.
- Identity: `<data>/peer/identity.json` (an Ed25519 seed and an X25519 private key, written once: temp file, fsync, atomic move). The card is `benbow1.` + base64url(Ed25519 public, X25519 public, 4 checksum bytes); its id (hex of the first 16 bytes of SHA-256 of the Ed25519 key) names the server in envelopes and folders; the fingerprint (10 bytes, five groups) is compared in person. A mistyped or cut card is refused.
- Letter `{id, seq, kind: note|ack, text?, acks[], sentAt}` sealed with HPKE (DHKEM X25519, HKDF-SHA256, ChaCha20-Poly1305, info = `benbow-letter/1|from|to`) into `Envelope {v: 1, from, to, sealed, sig}`; `sig` is Ed25519 over info + ciphertext and is checked before anything is decrypted. Another recipient, a bad signature, a damaged ciphertext or an unknown format: refused, logged and removed. A sender that isn't a contact: the letter stays until its card is added. As built 0.14.1 (ADR-044): an envelope `v` above this server's stays in the mailbox (never refused or removed) and «Связь» says to update; letters carry `server` (the sender's Benbow version, optional, ignored by older servers), kept per contact in `settings` (`seen.<contact>`) and shown under the friend's name. Optional fields and new kinds keep `v` (an older server keeps a letter of a kind it doesn't know in its inbox, and the code that knows the kind must also read those already there); a change an older server would misread raises it.
- Store `db/peers.sqlite` (`PeerDatabase`): `contacts`, `outbox (contact, seq, letter_id, kind, text, created_at, sent_at, acked_at)`, `inbox (contact, seq, letter_id unique, …)` and `settings` (the mailbox; the password is never shown back). Numbers are per contact.
- Round (`Courier`): read the own folder; keep each letter (`INSERT OR IGNORE`, so a double is kept once), acknowledge everything kept this round in one `ack` letter per contact (doubles too), then remove what was read; apply acks; then send what was never sent, and send again what was sent over 10 minutes ago, is unacknowledged and is no longer in the recipient's folder (a letter still there waits for an absent friend). A cut at any step repeats harmlessly.
- Carriers (ADR-055, C1, `Carrier.kt`): the courier only drops sealed bytes under random names into a box (`Address`: a card id and `LETTERS` or `PARTS`), lists, reads and removes its own, asks which names still wait in someone else's box and waits for an arrival; each carrier states its largest item, a daily budget, whether it tells of arrivals and whether items land whole. `ImapCarrier` (a mailbox), `FolderCarrier` (a folder some program keeps the same in both homes: parts in `Benbow/<id12>/`, letters in `Benbow/<id12>/letters/`, written in a staging folder and moved in, looked at every 10 s) and the tests' `MemoryCarrier` pass one contract test (`CarrierContractTest`).
- Mail (`ImapCarrier`, Angus Mail): one mailbox shared by both servers, IMAPS only, an app password. Letters in folder `Benbow-<first 12 of the recipient's id>` as plain text (as before ADR-055, so older servers read them), parts in `Benbow-<id12>-parts` as a base64 attachment of at most 8 MB, at most 150 MB a day from each server (Gmail stops IMAP for up to a day past 500 MB of uploads for the account); APPEND with the letter id as the subject; the own folder stays open in IDLE (9 minutes, ended early by a timer that touches the folder; read timeout 12 minutes; a server without IDLE is polled every 30 s). `PeerLink` reconnects after 5 s, doubling to 5 min, but a refused login is not retried until the settings change (a wrong password could get the mailbox locked). A queued note goes at once on a second thread (a failed try again after 3, 10 and 30 s), then wakes the worker. For two minutes after letters moved either way the worker asks the mailbox every 3 s instead of waiting in IDLE: Gmail tells of a new message in a label 10-30 s late. The store keeps its own connection between rounds (`separatestoreconnection`, pool timeout 10 min), so an APPEND doesn't log in again; IMAP steps over three seconds are logged, and each round that moved letters logs one line. Gmail should be set to delete messages expunged over IMAP for good.
- Every message gets its Message-ID from `mail.from` (2026-10-29): without it Jakarta Mail asked for the PC's own name at every APPEND, five seconds on the owner's network.
- Measured through Gmail between two servers on one PC (2026-10-19): a letter is in the mailbox 1-4 s after it is queued; a first letter to an idle server arrives in 12-30 s, replies during a conversation in 3-7 s, acknowledged in 7-11 s. Files through the owner's Drive mirror folder (on another disk than the data, both servers on one PC, so Drive's own sync between PCs not yet measured): an 8 MB file sealed and placed in 0.2 s, received in 12 s, the folder cleared in 29 s; the bytes matched.
- Files in parts (ADR-055, C2, `Transfers.kt`, `PeerFiles.kt`, `PeerFileRecords.kt`): the upload is sealed as it streams in with a key of its own (Tink streaming AEAD, AES-256-GCM-HKDF, 1 MB segments, the file id as associated data), so no plain copy is written, into `<data>/peer/outgoing/<id>.sealed`, kept until the friend has the file. The link's files thread (every 10 s while something is on its way, at once after a letter about a file) holds a carrier connection of its own, so a part never holds letters up. A pass takes in parts, finishes files, cuts and announces, then sends: a sealed file is cut every min(the carrier's largest item, 8 MB) bytes and announced by a `file-parts` letter (`PartedFile`: name, size, SHA-256, key, sealed size, part size, each part's SHA-256, `via`); part `n` is dropped into the friend's parts box as `<id>.<n>`, at most 64 MB unconfirmed at a time and within the carrier's daily budget (150 MB a day through the mailbox, counted per account over the last 24 h in `spend`; «Друзья» says until when parts wait). The recipient reads only parts of files it was told of, checks each against its length and SHA-256, writes it into place in `<peer>/incoming/<id>.sealed` (fsync) before it counts, then removes it from the box; a damaged part is removed from a carrier where items land whole (and waits in a synced folder, which may still be bringing it), a double is removed. Parts got are told by `file-got` letters (`PartsGot`); only the friend the file went to can mark them. A part unconfirmed after 30 minutes and gone from the friend's box is dropped again; one still there waits for an absent friend. With every part there the file is opened (any damage fails), measured against the letter, kept in `<peer>/received/<first 12 of the sender's id>/` under a safe free name and answered with `file-done`, after which the sender deletes its sealed copy and forgets the key. A `file-parts` letter kept while the server didn't know the kind is announced at the next start. Tables (schema 3, the store copied to `peers-pre-v3-<time>.sqlite` first): `files_out` and `files_in` gain `via`, sizes, `part_hashes`; `parts_out (file, n, dropped_at, got_at)`, `parts_in (file, n, got_at, told_at)`, `spend (at, carrier, bytes)`. Leftover half-sealed and half-opened files are deleted at start.
- Ways for files (C3, «Связь → Файлы», `files.via` in `settings`): `mail` (the letters' mailbox, on a connection of its own; the default), `parts-mail` (a second mailbox only for parts, `parts.mail.*` in `settings`, password never shown back) or `folder` (the shared folder set below it, through `FolderCarrier`, staging in `<peer>/staging`). Each way is a `Way` in `PeerLink` with its own carrier, opened only while files move that way and closed after, its own pauses after failures and a refused login not retried until settings change; why a way can't move files is shown in «Связь», in the file's bubble in «Друзья» and in the report. The budget is counted per mailbox account, so a second mailbox typed the same as the first shares its budget. Changing the way affects files sent afterwards: a file keeps the way it was sealed for.
- Files through Drive (F5a, servers 0.10-0.18, `DriveFiles`): a `file` letter announced a body sealed whole in `<Drive folder>/Benbow/<first 12 of the recipient's id>/<file id>.bin`, carried by the Google Drive desktop app. Such files (`via` = `drive`) are still taken in from the folder set in «Связь» (a body still syncing waits with its error shown) and answered with `file-done`; this server no longer sends through Drive.
- Admin page «Друзья» (loopback only, same-origin POSTs as the rest; the whole admin page is Material 3 in the client's Inn scheme, `AdminUi.kt` with `admin.css` / `admin.js` from the server's resources under a CSP that runs no inline script, so a friend's text can't act as code; a navigation drawer, a rail on narrow windows, with one section per tab: Сервер, Устройства, Копии, Голос, Друзья, Связь, a red dot on Копии or Связь when they need attention): «Связь» holds the mailbox and «Файлы» (the way files go, the second mailbox, the shared folder; folded when they work; the folder field has a picker: the server lists its own folders, `/admin/folders`, loopback only, suggesting folders named like Drive's mirror and marking the app's streaming disks as unfit), «Друзья» each friend as a conversation of notes and files with ✓ (in the mailbox) and ✓✓ (delivered), a file on its way with a bar of its parts, a composer with a paperclip, and exchanging cards (this server's card with a copy button beside the form for the friend's); the shown section refreshes itself every 4 s (`/?part=friends`, `/?part=link`) unless something is being typed there. Routes: `/admin/peers/mail`, `/drive`, `/contacts`, `/contacts/{id}/note`, `/contacts/{id}/file`, `/contacts/{id}/remove`, `/check`.

## API versioning and docs
- Major version in the path (`/api/v1`). Within v1 changes are additive only. Breaking changes go to `/api/v2`, and the server serves both during the transition.
- `protocol` integer for sync semantics. Clients outside `[protocol_min, protocol_max]` must not push. They show "update app/server".
- OpenAPI generated by the Ktor Gradle plugin (compiler extension) + `ktor-server-routing-openapi` annotations. Swagger UI or Scalar at `/api/docs`, spec at `/api/openapi.json`. Changelog in `docs/api-changelog.md` (created with the first endpoint).

## Test plan
A deterministic simulator in `shared/core` + `server` tests: random ops across N clients, network drop, duplicate, reorder, client kill mid-push, server restart, restore-from-backup (epoch bump). Assertions: (a) every revision ever created exists on the server once outboxes drain, (b) all clients converge to the server state, (c) no op is applied twice.

## Speech model
The voice-transcription model (ADR-025) is not journal data and isn't synced or backed up: the server keeps it in `<data>/models/<id>/` after the owner presses «Скачать модель» on the admin page (`SpeechModel`: pinned URLs and hashes from `SpeechModelSpec` in `shared/core`; anything that doesn't match is thrown away). Phones fetch it with `SpeechModelStore` into `files/models/<id>/`, resuming with Range, and check each file against the same pinned hashes (not the server's list); a `verified` marker saves re-hashing 230 MB on every start. Transcripts are the entry field `transcript:<attachment id>`. A sound's tags (ADR-035) are the entry field `track:<attachment id>`, set by the device that attached it right after the link (`entry.meta.set`, no protocol change).
