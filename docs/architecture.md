# Architecture (proposed, pending confirmation, see decisions.md)

## Stack summary
| Layer | Choice | Why |
|---|---|---|
| Language | Kotlin 2.4 everywhere (clients and server) | One language and shared types: models, content codec, sync and merge logic, API DTOs. Less AI context |
| UI | Compose Multiplatform 1.12.x: Android, Desktop (JVM), Web (wasmJs) | One UI codebase for three targets. Android is the primary target. Web is Beta (see research.md) |
| Design | Material 3 + Expressive APIs (experimental opt-in), wrapped in our own `BenbowTheme` tokens | Expressive is still alpha in CMP. Our wrapper absorbs API churn |
| Content | Benbow Document v1 = Portable Text-based JSON (content-format.md), exporters to MD/HTML/text/PDF | Rich formatting, lossless 1:1 storage, stable block keys |
| Client DB | SQLite via SQLDelight 2.x (Android and JVM) | SQL-first and transparent. Migrations verified by tooling. FTS5 |
| Web client | Thin, online-only, served by the server | Web SQLite persistence is immature. On LAN the server is always next to the browser |
| Server | Ktor 3.x on JVM, SQLite (xerial sqlite-jdbc) via SQLDelight | Shares code with clients. Stable and well known |
| Packaging | jlink runtime + jpackage app-image + WinSW Windows service, optionally wrapped by Inno Setup | Standalone, autostart, auto-restart, no Docker. GraalVM native-image is a possible later optimization |
| API | REST + JSON under `/api/v1`, OpenAPI generated by the Ktor plugin, docs page at `/api/docs` | Versioned, documented, Monbooru-style built-in docs |
| Sync | Outbox of idempotent ops + append-only revision DAG + server-side 3-way merge, LWW (HLC) for metadata | Never loses data, debuggable, no CRDT dependency (see sync.md) |

## Runtime topology
```
[Android app]  offline cache + outbox ──HTTPS(LAN) /api/v1──┐
[Desktop app]  offline cache + outbox ──localhost / LAN─────┤
[Browser]      thin web client (wasm, served by server) ────┤
                                                            ▼
                         benbow-server (Windows service, Ktor/JVM)
                         ├─ <data>/db/benbow.sqlite   (WAL, synchronous=FULL)
                         ├─ <media root>/YYYY/MM/...  (user-chosen folder, immutable files)
                         ├─ <data>/backups/           (verified snapshots, GFS retention)
                         ├─ <backup target>/          (second disk / NAS / cloud folder mirror)
                         ├─ <data>/export/            (human-readable Markdown mirror)
                         └─ admin page "/", API docs "/api/docs", web app "/app"
```
The server being unreachable is normal: clients keep working and sync later.

## Module layout (start small, split when a module exceeds ~15k LOC or build times hurt)
Scaffolded so far: `shared/core`, `shared/ui`, `apps/{android,desktop,web}`, `server`. `shared/client` arrives with Phase 2. `build-logic/` arrives only once duplication between build scripts starts to hurt.
JVM toolchain 17 for all modules (foojay auto-provisioning). Namespace `app.benbow`.
```
build-logic/        Gradle convention plugins (later)
gradle/libs.versions.toml
shared/core/        KMP, all targets incl. server JVM. Pure Kotlin: ids (UUIDv7), time/day logic, domain
                    model, Document codec + canonicalizer + exporters/importers, sync protocol DTOs, diff3 merge, HLC, validation
shared/client/      KMP android/jvm/wasm: Ktor API client, repository interfaces.
                    `nonWebMain`: SQLDelight cache, outbox, sync engine. `wasmJsMain`: remote-only repositories
shared/ui/          CMP android/jvm/wasm: BenbowTheme/design system, editor, screens, navigation, ViewModels
apps/android/       Android entry, platform services (WorkManager, notifications, media capture, widgets,
                    QS tile, share target), baseline profiles
apps/desktop/       Compose Desktop entry + MSI packaging
apps/web/           wasmJs entry. Build output is embedded into the server distribution
server/             Ktor app: routes, storage, blob store, backups, mirror export, admin page, packaging
docs/
```
Dependency rule: `apps/* → shared/ui → shared/client → shared/core`; `server → shared/core`. Nothing depends on apps.

## Client architecture
- Unidirectional data flow: ViewModel (androidx lifecycle KMP) exposes `StateFlow<UiState>`. UI sends intents. Repositories are the single source of truth backed by the local DB (Flow queries).
- Optimistic local writes: write to the DB and outbox in one transaction, update the UI instantly, then the sync engine pushes in the background.
- DI: Koin (simple, KMP, well known). Navigation: Navigation 3 (CMP 1.10+). Images: Coil 3.
- Performance: immutable UI models, stable keys and `contentType` in lazy lists, paging by cursor, prefetch of adjacent entries, baseline profiles, R8 full mode.

## Server internals
- Single write connection (serialized writer) + read pool, like Monbooru. All mutations are transactional and append `change_log` rows in the same transaction.
- Services: `SyncService` (push/pull), `BlobStore` (resumable upload, verify, place), `RevisionService` (DAG, merge), `BackupService` (scheduler, verify, retention, mirror), `ExportService` (Markdown mirror, ZIP export), `SearchService` (FTS5), `PairingService`.
- Admin page: server-rendered HTML (kotlinx.html), independent of the wasm app so it keeps working if the web client breaks. Shows status, last backup, integrity, devices, pairing QR, "backup now".
- Config: `<data>/benbow.toml`. Logs: `<data>/logs/`, rotated.

## Packaging and deployment (Windows)
1. `jlink` builds a minimal runtime, `jpackage --type app-image` produces `benbow-server/` with an exe launcher.
2. Bundle WinSW (`benbow-server-service.exe` + `.xml`): auto start (delayed), restart on failure, log rotation.
3. Optional Inno Setup installer: copies files, registers the service, opens the admin page for first-run setup (data dir, media dir, backup target, pairing).
4. Updates: stop service → automatic DB backup → replace app-image → start → migrations run (see data-safety.md).
Desktop client: Compose `packageMsi`. Web client: static files served by the server.

## Testing strategy
- `shared/core`: unit + property tests (kotest-property): Markdown round-trip, diff3 merge, HLC ordering.
- Sync: deterministic simulation (N clients + server in memory, random ops, drops, duplicates, reorders, crashes). Assert convergence and that no revision is lost.
- Server: Ktor `testApplication` against a temp-dir SQLite. Migration tests against fixture DBs from every schema version. Backup/restore tests.
- UI: Roborazzi screenshot tests (JVM). Desktop smoke via Compose Hot Reload MCP. Android macrobenchmarks for startup and scroll (Phase 6).
- `./gradlew check` is the single gate.
