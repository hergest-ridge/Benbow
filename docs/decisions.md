# Decisions (ADR log)

Status: **P** = proposed, **A** = accepted, **R** = under review, **S** = superseded. Keep each entry ≤10 lines. Append, don't rewrite history.
Owner review on 2026-10-12: everything accepted. ADR-005 is superseded by ADR-015. ADR-006 is still gated by the spike.

### ADR-001 Kotlin everywhere [A]
Clients and server in Kotlin 2.4. Shared `shared/core` (models, content codec, merge, sync DTOs).
Alternatives: Go or Rust server (single binary, but duplicates models and sync logic in a second language, which means more AI context and drift).

### ADR-002 Compose Multiplatform for all clients [A]
One UI codebase for Android, Desktop (JVM) and Web (wasmJs). Web is still Beta (canvas-rendered, weaker browser-native text features, multi-MB bundle), which is acceptable for a personal LAN app.
Alternatives: native Android + separate TS web app (two UIs), Flutter (Dart, worse Android-native feel and no Kotlin sharing with the server).

### ADR-003 Desktop-first iteration, Android right behind, web thin [A]
Desktop JVM is the main dev target (Hot Reload + MCP). Android builds from the first scaffold, so an installable debug APK exists from Phase 1 (the owner wants mobile ASAP). Web is online-only, served by the server at `/app`, compiled in CI from day one, polished later.

### ADR-004 SQLite + SQLDelight on server and clients [A]
Server: WAL, `synchronous=FULL`, single writer + read pool (Monbooru pattern, but stricter durability). FTS5 for search. Android must use a SQLite build with FTS5 (bundled driver). Verify in Phase 1.

### ADR-005 Canonical content = restricted Markdown subset [S → ADR-015]
The owner rejected limiting formatting to what Markdown can express (2026-10-12).

### ADR-006 Editor = single rich `BasicTextField` (Compose 1.12 styles API) [A, 2026-10-12]
Seamless selection, native IME, works on all targets. The spike passed on the S24+ (editor.md "Spike findings"). Architecture: model-first (`RichText` + own undo), styles rendered in `OutputTransformation`, zero-width glyphs at style boundaries, IME bridge and clipboard repair. **Scale limit:** smooth up to ~5k chars; long-form text (writer module) will need a chunked or `EditText`-based engine.

### ADR-007 Sync = outbox ops + append-only revision DAG + server diff3 merge + HLC LWW metadata [A]
No CRDT. Conflicts keep both heads. Store identity and epoch protect against restores and wrong servers.

### ADR-008 Server = jlink runtime + WinSW Windows service [A]
Refined in the spike: runtime is Temurin 25 LTS via jlink (JBR has no jmods; jpackage is unnecessary), and WinSW v2.12.0 (NET461, SHA-256 pinned in the build) starts `java.exe`. The server sets `jdk.net.unixdomain.tmpdir` itself (some Windows profiles break NIO in %TEMP%).
Autostart before login, restart on failure, no Docker, no system JRE. GraalVM native-image optional later.

### ADR-009 Attachments = immutable files with human-readable paths in a user-chosen folder [A]
`<media>/YYYY/MM/YYYY-MM-DD_HHMMSS_<shortid>.<ext>`, SHA-256 verified, deduplicated in DB, resumable chunked upload.

### ADR-010 Backups from v1 [A]
Verified SQLite snapshots (GFS retention) + mirror to a **second local disk** (DB + media) + human-readable export mirror. No cloud target for now.

### ADR-011 REST/JSON `/api/v1` + generated OpenAPI + `/api/docs` [A]
Additive-only within v1. Separate `protocol` integer for sync semantics.

### ADR-012 Pairing + bearer tokens + TLS from v1 [A]
One-time code / QR → device token. Self-signed certificate generated on first server run. Clients pin its SHA-256 fingerprint received during pairing. Web: one-time browser certificate exception.

### ADR-013 Docs and code in English, conversation in Russian [A]
English needs roughly half the tokens of Russian for the AI workflow. App UI strings in Russian (resources, i18n-ready).

### ADR-014 One `entry` entity with `kind` (journal/post/note/comment) [A, "for now"]
Shared editing, revisions, attachments, tags, search. Views are queries.

### ADR-015 Canonical content = structured JSON document based on Portable Text + exporters [A]
Formatting isn't limited by Markdown. Storage is a 1:1 serialization of the editor model (no parsing round-trip). Every block has a stable `_key`, which enables precise merges, ink anchoring and fragment links. Markdown, plain text, HTML and PDF become exporters. The export mirror writes `.md` + `.json` per entry. Colors and sizes are theme tokens.
Alternatives: plain MD (too limiting), MD + inline HTML (fragile), MD dialect with attributes like Djot/Pandoc (custom parser, other apps show noise anyway).

### ADR-016 Android baseline [A]
Target device Galaxy S24+ (Android 16, 120 Hz). minSdk 34, target/compile = latest stable. Performance budgets are measured on this device. IME tests cover Samsung Keyboard and Gboard.

### ADR-017 Formatting scope v1 + palette tokens [A]
Inline: bold, italic, underline, strike, code, highlight, text color, size steps, spoiler, link, entry link. Blocks: h1–h3, align, quote, callout, checklist, nested lists, divider, code block. Later: inline media, tables, toggles as atomic embeds. Colors and sizes are theme tokens (dark mode and note-background aware), never raw hex. Spec: content-format.md.

### ADR-018 Identity: the "Admiral Benbow" inn [A]
A cozy home base and Jim Hawkins's journal (Treasure Island, public domain). It shapes the icon and light visual accents. Original art only, no Disney assets. See vision.md#identity.

### ADR-019 Server restore = new epoch + reconciliation from device caches [A]
Restoring a snapshot (`--restore`, or a hand-copied file noticed via `db/high-water.properties`) moves the store to an epoch past every one this data folder has seen. Devices that see a new epoch (or a server cursor below theirs) ask which of their entries and heads the server lacks and re-push them, then pull from 0. A re-pushed head goes without parents: if the server kept an older head, both stay as a conflict and the user picks. Devices don't keep revision ancestry, and a silent fast-forward could hide edits made after the restore.

### ADR-020 Attachments: content-addressed files + LWW links in the entry [A]
Files are stored and transferred by SHA-256 (dedup, verification, resumable upload); the server places them at human-readable paths (ADR-009). The link to an entry is an `AttachmentState` in the entry, last writer wins per link by HLC, and carries the immutable file meta, so one op type (`entry.attachment.put`, protocol 2) covers add, reorder, caption and remove (`present = false`). A link may sync before its file; clients show it as pending.

### ADR-021 Entry metadata = namespaced LWW fields [A]
Favorite, pinned, mood, tags, reactions and a comment's parent are `entry.meta.set` fields: `favorite`, `pinned`, `mood`, `tag:<lowercase name>` (value = display name, null = removed), `reaction:<emoji>`, `parent` (later: `start`, `at`, `repeat`, `done`, `background`). Each key has its own HLC, so concurrent changes to different tags merge, and restore reconciliation already re-pushes fields. No protocol change. Tag categories and colors (4.3) live in a registry, not in the field key. Replaces the planned `entry.tag.set` / `reaction.set` ops.

### ADR-022 App lock = the platform's owner check, per device [A]
The lock (6.4) uses Android's `BiometricPrompt` with `BIOMETRIC_STRONG | DEVICE_CREDENTIAL`: fingerprint or face, with the phone's screen lock as the way in. No app PIN, so nothing secret is stored and a forgotten code can't lock the owner out of their own diary; without any screen lock on the device the app doesn't lock. It gates the UI only (files rely on device encryption), never applies to quick capture (it shows nothing), lives in local settings (not synced), starts locked in every new process and re-locks after 1 min / 5 min / 1 h / 5 h away. Recents shows a blank card while it is on. Desktop: none yet.

### ADR-023 Moving an entry in time = the LWW field `when` [A]
An entry's `day` and `createdAt` come from `entry.create` and never change (the server and the mirror keep them, so mirror file names stay stable). Moving it sets the field `when` = local "YYYY-MM-DDTHH:MM"; each client rewrites its local `day` and `created_at` columns from it after every local change and every pull (`Moments`), so lists, the calendar and the day view show it there on every device. No protocol change; restore reconciliation re-pushes it like any field. The export's front matter carries `when` next to the original `day`.

### ADR-024 Release = R8 without obfuscation, baseline profile from a non-minified build [A]
Release (and the `benchmark` build) shrink and optimize with R8 (`proguard-android-optimize`, resource shrinking) but `-dontobfuscate`: crash traces from the owner's phone stay readable, class names in error messages stay true, and the baseline profile matches code as written. The profile is collected by `BaselineProfileGenerator` on the `profiling` build (same as `benchmark`, no R8) and committed as `src/main/baseline-prof.txt`; R8 rewrites it for its own changes. No androidx.baselineprofile Gradle plugin: its generated `benchmarkRelease` build would carry the release id and key, i.e. install over the owner's app. Regenerate after big UI changes (command in CLAUDE.md). R8 was verified on the bench build: pairing and a full sync of 430 entries and 240 files against a dev server.

### ADR-025 Voice transcription = GigaAM v3 on the phone, in a sandbox, model only from the own server [A]
Voice notes become text on the phone, offline: GigaAM v3 RNN-T with punctuation (MIT; sherpa-onnx's official ONNX package), run on ONNX Runtime 1.30 (Maven Central, arm64 only) in `AsrService`, an `isolatedProcess` service: no permissions, no network (checked on the S24+: DNS and sockets refused), no app files. The model arrives as descriptors and is mmapped into `createSession(ByteBuffer)` (the sandbox can't open files by path, so sherpa-onnx itself, path-only, was dropped); audio comes through a pipe; only text returns. Kaldi fbank, piece cutting at quiet moments and greedy decoding are ours (`app.benbow.core.speech`, after sherpa-onnx's reference script). ONNX Runtime's telemetry provider is removed from the manifest; in the sandbox it can't reach the network anyway. The model reaches the server only on the owner's click (pinned URL, parallel ranges, pinned SHA-256 of the archive and each file; the server's only internet request); phones fetch it only from the paired server and check the same pinned hashes in their own build. Text lives in the LWW field `transcript:<attachment id>` (ADR-021), is searchable and exported as a quote. Measured: ~1 s to load, 20× faster than real time. Rejected: Android `SpeechRecognizer` (live dictation, vendor-dependent), ML Kit GenAI (alpha, Pixel 10 only), Whisper (slower for Russian).

### ADR-026 Drawings = SVG attachments with their strokes inside [A]
The owner chose drawings in notes, by finger, as the first ink feature (paper pages and margin marks stay in editor.md for later). A drawing is an attachment of kind `drawing`: a plain SVG (filled pen outlines and see-through marker lines in the light theme's colors, so any browser or Obsidian shows it) with the strokes themselves as JSON in `<metadata><benbow-ink>` (canvas 1000 units wide, points x/y/t, tool, palette token, size), which the app reads to edit and to draw in the theme's colors. It sits in the text as an `attachment` block like a picture and syncs like one: no protocol change. Attachment meta is immutable, so a redraw saves a new attachment, the text points at it and the old link becomes absent; the server never deletes files, so earlier versions stay. A finger has no pressure: pen width follows speed. Geometry and the codec live in `app.benbow.core.ink` (tested); the drawing screen is a navigation route that hands its result to the editor through `AppServices.drawn`, saved from `ViewModel.onCleared` (not on rotation).

### ADR-027 Calendar = its own store beside the journal; ICS by file [A]
Owner, 2026-10-15: calendar events are context for a day, not journal content; they are worth less than entries and will outnumber them, so the two must not share storage or code paths. The calendar gets its own store: server `db/calendar.sqlite` (calendars, events, change log, applied ops, schema version, migrations, epoch), endpoints `/api/v1/calendar/push|pull` with their own cursor, client `calendar.db` with its own outbox. The journal DB is never touched by calendar code. Records are LWW per field (HLC); no revisions, merges or conflict heads. Kept cheap guarantees: op ids, outbox until acknowledged, soft delete, verified backups (own snapshots; a calendar failure never stops the journal's). Shared: server process, pairing and token, HTTPS, HLC, backup disk. The journal syncs first; a calendar failure doesn't block it. 5.1 events (entries of kind `event`) move once to «Мои события» with the same ids and the old entries go to the trash. Reminders stay entries for now.
UI: events live only in the Calendar tab (calendars with colors and show/hide checkboxes like Google, quiet dots and multi-day bars under the journal's dots and mood tint, a compact strip in the day, an event sheet instead of the editor, «Написать об этом» opens a journal entry); never in Home, Feed, search, stats, tags or the journal export.
ICS: import from files only (Google's export ZIP holds one `.ics` per owned calendar; each becomes a calendar), a preview with per-calendar checkboxes and a period (all by default), dedup by UID, batch undo to the trash; export one `.ics` per calendar (Calendar tab, archive ZIP, server mirror), reminders not exported. Own codec in `shared/core` (ical4j is JVM-only). URL subscriptions later, only through the server.
Rejected: events as entries (every journal query must filter them out, cf. the `daysWritten` bug; event schema changes would migrate the journal DB; imports would write into it) and separate tables in the journal DB (still the journal's file and migrations, one sync stream).

### ADR-028 ICS = floating local times out, the device's zone in [A]
Benbow keeps event times as local wall time without a zone ("2026-10-14T09:30"), like the rest of the app. Exports (7.3c: the server's `export/calendars`, the app's ZIP and "Сохранить .ics") write them as floating DATE-TIMEs (no TZID, no Z) and all-day events as DATEs with an exclusive DTEND, so nothing is invented: Google, Apple and Outlook place floating times in the calendar's own zone, and weekly 09:30 stays 09:30 across DST without writing VTIMEZONE blocks (kotlinx-datetime can't produce their rules). Imports (7.3d) convert TZID and UTC times into the importing device's zone. UID = the event's own `uid` from an import, else `<id>@benbow`, so re-imports elsewhere update instead of duplicating; Benbow's color travels as `X-BENBOW-COLOR`. The codec is ours, in `shared/core` (`Ics`, `CalendarExport`): checked on 2026-10-15, there is still no Kotlin Multiplatform iCalendar library (only JVM ones, e.g. iCalDAV's icalendar-core).

### ADR-029 Web = the same app compiled to wasm, a full client for PCs on the LAN [A]
Owner, 2026-10-15: the web version becomes a priority, used only on PCs in the home network; offline at most shallow. It is not a second UI: `shared/client` and `shared/app` gain a wasmJs target, so the browser runs the same Compose screens, view models, repositories, sync and calendar as desktop and Android. Only platform pieces differ behind expect/actual, as between Android and desktop: the HTTP engine (the browser's fetch, which also judges the self-signed certificate after a one-time exception), the SQLite driver, files and pickers, playback (the browser's own video/audio element). The local DB is SQLite built for wasm (sql.js 1.14, SQLite 3.49: the official sqlite-wasm build has no FTS4, which search uses), in memory on the main thread behind a synchronous SQLDelight driver (the official web driver is asynchronous and would turn every query of the client into a suspend call), with its whole file saved to IndexedDB shortly after writes (a put is atomic, so the stored file is always a complete snapshot; one tab owns the data via Web Locks, a second tab is refused): a reload starts fast and a short server outage loses nothing; closing the tab with unsent changes asks first. Served by the server at `/app`, paired with a code like any device. Supersedes ADR-003's "web thin, online-only, shared/ui only". Not on web: voice transcription, the widget, app lock (for now); reminders only while the tab is open.

### ADR-030 The web page reaches nothing but its own server [A]
2026-10-16 (W4): Compose for Web fetches glyphs it lacks (emoji, rare scripts) from fonts.gstatic.com at run time, which would tell Google when and from where the journal is open. Two layers stop it. The server sends a Content-Security-Policy with `/app/` (`connect-src 'self'`, `font-src 'self' data:`, scripts only from itself plus `'wasm-unsafe-eval'`, workers only from itself or `blob:`: Coil decodes pictures in one), so the browser refuses any other host whatever a library tries. And the app bundles Noto Color Emoji (OFL, from `@fontsource/noto-color-emoji`, Google's ten slices with the SVG table dropped at build time: Skia draws its COLRv1 glyphs but leaves SVG ones blank) and preloads it before the first frame, so emoji draw without a network. A character no bundled font has shows as a box instead of being fetched. 2026-10-17: so the UI's own texts keep to Latin, Cyrillic, common punctuation and emoji; arrows, stars, triangles and other symbols are drawn as icons (`Icons.kt`, `EditorIcons.kt` in shared/ui), and `UiGlyphsTest` fails on any other character in the app's strings. Symbols the owner types into notes may still show as boxes on the web; bundling Noto Sans Symbols 2 and Math the way emoji are bundled would cover them.

### ADR-031 Бережно: the entry says what it is, the moment decides what shows [A]
Owner, 2026-10-16: some entries are sad or triggering yet part of the journal; sometimes they belong in view, sometimes not. Three tools, mildest first. The inline spoiler: text under a shimmering particle mask wherever rich text is drawn; a tap opens all of the entry's spoilers until it leaves the screen; in the editor it is frosted and clear at the cursor. The curtain: the entry keeps its place but shows only its time at one compact height, without tags, mood, pictures or even its length. Quiet: gone from passive places, with no gap, count or marker.
Marks: by hand per entry (synced LWW field `veil`), and rules by tag, tag category or a named period of days (a synced registry, each rule with a level; new rules start as curtain). The entry's own mark wins over the rules; `open` shows it despite them. A mood rule later; never guessing from the text. Passive places hide (Feed, Home with On this day and the resurfaced favorite, widget, notifications); places the owner searches show quiet entries under the curtain (search, a calendar day, entry links), so nothing ever seems lost.
The mode is per device, on by default. Turned off, it comes back by itself after 5 minutes away and in every new process: opening is temporary, closing lasts. The switch is out of sight: pull the Feed down at its top (like Telegram's archive) or long-press the Feed tab; desktop and web also click the Feed's title. Nothing in the feed says that something is hidden.
It is a view only: text, revisions, sync, backups, stats and exports are untouched (the export carries `veil`). "Отложить до…" (quiet until a day, then a calm card on Home) comes last. No fingerprint for curtains (owner).

### ADR-032 Tags and tag categories by id; the old keys are the ids [A]
Owner, 2026-10-16, before real tag and category editors: names as keys tie everything to a spelling, and Бережно's rules (ADR-031) pointed at names, so a rename would have let quiet entries out. Now a tag is its id: the entry's LWW field `tag:<id>` holds the name it was put on with, the registry (`system-tags`) has `name:<id>` once the tag has a name of its own, and that wins. Categories too: `cat:<tag id>` = the category's id, `catname:<id>`, `catcolor:<id>`.
No entry is rewritten. A tag from before keeps its key (the name in lower case) as its id, a category its lower-case name, so colors, categories and rules work as they did and an older journal reads exactly as before; new tags and categories get new ids (a uuid). A full rewrite onto uniform ids was rejected: no visible gain, the riskiest kind of change (every tagged entry, from every device), and late ops from older versions would need translating. It stays possible later.
Rules point at ids; one made before by name also matches by name, so a rule can cover more, never less. 7.9 T2: everything done to a tag or category is a registry field and entries never change, so each step is undone exactly: `into:<id>` merges a tag into another (entries read as the target, the old name leads to it, `splitTag` undoes it; merges in a circle from two devices end at the smallest id everywhere), `trash:<id>` / `cattrash:<id>` put them in the trash (gone from chips, lists and suggestions; back from «Корзина»; «Эмоции» can't go), `archived:<id>` keeps a tag out of suggestions only. Бережно's rules see the ids an entry carries, through merges, the trash and trashed categories: nothing done to tags lets an entry out. 7.9 T5: exports carry the registry itself as `tags.md` and `tags.json` (`TagBook`), so ids never have to be read by a person. Names are not keys any more: two tags may share one (two «Саша»); typing a name picks the tag with it. Exports list tags by the registry's names (the server's mirror reads the registry and writes again the notes of a renamed tag); the `.json` sidecar gets `tags: [{id, name}]`. Protocol unchanged. Older app versions show new tags by the name on the entry but can't take them off: update every device.

### ADR-033 Dictation = two recorder keys; phrases cut on the phone, recognized in the sandbox [A]
Owner, 2026-10-17: a voice note is often not wanted, but text said straight into a note is. Two separate keys like a mechanical dictaphone's (the owner's pick over one key with hold-and-slide gestures): «голос» records a voice note as before, «текст» dictates. A tap latches a key until the next tap, holding records while held, and pressing one key while the other is down lets that one up with its take kept (a tape deck's interlock). Lamps follow the voice; haptics only, no sound (it would get into the take). Quick notes get the текст key too. UI in ux.md (7.10b-e).
Engine (7.10a): the microphone's 16 kHz samples are cut into phrases on the phone as they come (`PhraseCutter` in `shared/core`: 700 ms of quiet after 250 ms of speech; speech means about 10 dB over the quietest frame of the last 3 s; at most 20 s, cut at the quietest moment like `speechPieces`), and one sandbox session (ADR-025) recognizes them in order (`dictate`, `Recognizer.samples`), so a phrase's text shows while the next is said.
Measured on the S24+ with the phone's TTS (bench build, no microphone): phrase by phrase gives the same words as whole takes (no word wrong in three cases, 15-28 s), each phrase is text 170-260 ms after its cut, so about a second after one stops talking. A pause inside a sentence makes the model start a new one (a capital, sometimes a period for a comma): `fitPhrase` puts that first letter in lower case after text with no end mark; commas stay the model's call.
Nothing said is lost: when the microphone or recognition fails, or speech yields no words, the take is kept as a voice note (the screen says so at once). After a good take its audio is deleted, with «Приложить запись» on the snackbar for a few seconds (owner). The take is written to disk as it's recorded; one a dead process left becomes a voice note on start (data-safety.md). Takes are recognized one after another (a quick second take waits its turn; the microphone never does). As built (7.10b-e): `RecorderKey` and `RecorderKeys` (mechanics, tested), `Dictations` (service, tested with a made-up microphone), `AndroidDictationMic` (`AudioRecord` from `VOICE_RECOGNITION`, WAV, AAC by `MediaCodec`), `EditorState.insertDictated`; «Заменить текстом» hides the voice note (`removeAttachment`, back with `restoreAttachment`).
Rejected: Android `SpeechRecognizer` and the keyboard's dictation (ADR-025: the vendor's cloud, weaker Russian); streaming the whole take into the sandbox to cut it there (the cutter needs no model, and the sandbox stays a pure audio-to-text function).

### ADR-034 Home = the owner's blocks in one synced layout [A]
Owner, 2026-10-17: Home should be arranged by hand and grow with new blocks. It is a list of blocks (type, size, settings) in the owner's order, one layout for every device: the system entry `system-home` (like `system-gentle`) with LWW fields `block:<id>` = `{type, size, config}` and `order` = the ids. Until the first change it has no fields and the default (Home as it was) shows, so a better default still reaches the owner; the first change writes it whole, later ones only what changed, so a block added on another device meanwhile stays (blocks `order` doesn't name come last). A type or size this app doesn't know is kept, never drawn, removed or rewritten; new settings go into `config`.
Grid: two columns on a phone, more on a wide Home in the same order. S is half a row, M a row, L a row in a larger form, a list a row as tall as its entries (lazy items). Rows fill in order and share out room left (a lone S is as wide as its row); nothing moves by itself. An empty block leaves no gap (the empty day stays: it invites). Cards that come for a reason (an entry back, the reviews) sit above the blocks, the kindness card under the check-in. Blocks that look back (On this day, favorites, tag galleries) are passive places (ADR-031). Stats only count up: no streaks, no comparisons.
Editing: a schematic of the grid with ↑/↓, sizes, settings, remove (with undo), a catalog, «Вернуть обычную главную», and a block's long-press menu. Rejected: a layout per device (one Home is "mine"; per device can come later), dragging on Home itself first (buttons work with a mouse and keys too; dragging later), a tall 1×2 size for now (breaks simple rows). Not content: not exported; protocol unchanged.

### ADR-035 Sounds from elsewhere and one player for every sound [A]
Owner, 2026-10-17: any sound file can join an entry (mp3, m4a/aac, wav, flac, ogg/opus, aiff: whatever the device plays), and the app gets one player for all sounds, voice notes too. Android adds «Аудио» to the editor's media row (the system's file picker, `audio/*`); desktop and web attach through their file dialog and drops as before; sharing to Benbow already takes any file.
Tags are read once, when the file is attached, by our own reader in `shared/core` (`TrackReader`: ID3v1 and ID3v2.2-2.4, MP4 `ilst`, FLAC and Ogg comments, WAV and AIFF chunks; text labelled Latin-1 that is really cp1251 or UTF-8 is recognized), so every platform gets the same answer (Android's `MediaMetadataRetriever` garbles cp1251 tags). Title, artist and album go into the LWW entry field `track:<attachment id>` = `{"title","artist","album"}` (like `transcript:`), written in the attach transaction; the embedded cover becomes the attachment's preview (a JPEG up to 1024 px, so the player's large cover stays sharp). No protocol or server change: older apps keep the field and show the file name. Rejected: new `AttachmentMeta` fields (an older server rejects them, an older app re-pushing a link drops them).
A sound shows like a voice note: a row with the cover (or the play button), the title (the caption given by hand, else the tag, else the file name), the artist and the length; the feed lists every sound of an entry under its text, wherever it sits in the document. A sound whose tags name an artist is music: no transcription is offered or done for it (a recorder may title its files, never with a performer). Search finds title, artist and album.
The player (`AudioPlayer`, common) keeps a queue over a platform engine. Started in the feed it plays the entry's sounds, then those of the entries below it (older ones: the feed reads newest first, top down), skipping entries under a curtain or quiet (ADR-031); started elsewhere (a post, the editor, comments, search) it plays that entry's sounds. «Назад» restarts a track after 3 s, else goes to the one before; after the last track it stops on it, paused.
Mini-player: a thin strip above the tab bar (on wide windows at the foot of the content; on a phone a post shows it above its comment box) while a track is loaded: play/pause, title and artist, «Следующий» while playing, ✕ while paused (closes the player). A tap opens the player screen like a streaming app's: the large cover, colors from it, title, artist, album, a seek bar with times, previous / play / next, the entry it comes from; a swipe down or Back closes it.
Engines: Android plays in a `MediaSessionService` (media3-session, the same Media3 as before; the service adds its session itself, since no controller of ours ever connects and Media3 shows nothing until one does): notification, lock screen, headset and Bluetooth buttons, audio focus, a pause when headphones go; next and previous from there go to the app's queue. Desktop plays with JavaFX Media 21 (mp3, aac/m4a, wav, aiff); what it can't play opens in the system player as before. The web uses the page's one `<audio>`.

## ADR-036: The feed over the whole journal, and finding one's way in it (2026-10-17)
The feed held the 300 newest posts with their bodies; older ones were out of reach. Now (7.13 N1) it reads in two layers: an index of every post (`feedIndex`: id, day, time, whether it has media, and the marks Бережно goes by; no text, transcripts or attachments) gives the list its true length, order and veils, and the posts themselves (`feedItems`) come in windows of 40-post chunks: those on screen and one on each side; a post outside its window is a placeholder of about its height. The index and its window come out together, so a new post never shows as a placeholder first. A jump reads its window before it scrolls. Reads only: no schema, sync or server change.
Finding one's way (owner 2026-10-17, plan N1-N6 in roadmap.md): the month in view under the title, «К сегодня» once a few screens down; keys and the middle button on desktop and web; a date scrubber (on by default, can be turned off); «Перейти» (years × months, today, a year ago, a date, at random); filters (tags and categories, any of them; years) as a lens; «Показать в ленте». Jumps first, filters second. Keys and the middle button (N2) are one modifier over any scrollable (`pageScrolling`): the feed, a post, search; the browser's own middle-button actions are turned off on the page.
Psychology: navigation shows no numbers, gaps or mood; quiet and put-off entries leave no trace in it (ADR-031); a tag filter is deliberate like search, so that tag's quiet entries show under a curtain; filters aren't kept between runs; back after five minutes away, a feed on screen starts at today.
Rejected: a higher limit (every change re-reads every body); Paging 3 (jumps to any place fight its model, and it is one more dependency for every target).

## ADR-037: The calendar's months by swipe and an overview of the years (2026-10-18)
The calendar changed months only with ‹ ›, so an old entry meant leafing blind, and a day's entry opened for editing. Now (7.14, owner 2026-10-18): the grid is a pager of months (1900-2199), neighbours composed ahead and the last marks of twelve months kept, so a swipe never shows an empty grid; its height glides between four and six weeks with the swipe. A settled month picks today there, else its first day with entries, else the 1st; a day picked meanwhile wins. ‹ › only with a mouse; «Сегодня» once away. The title («🍂 Октябрь 2026 ▾») opens «Обзор»: each year with entries as twelve small months with a dot per day with entries, from `entryDays` (one `DISTINCT day` query, no fields read). An empty month points to the nearest entries either way. A day's entry opens read-only, as in the feed, and so does one from search, a tag's page, Home and Бережно's lists; drafts, the trash and comments open for writing.
Psychology: the overview shows where the journal is full by dots alone: no numbers, streaks or percentages, a day without entries is a faint speck rather than a hole; entries only (events are context, ADR-027, and an imported calendar would cover it); quiet and put-off entries keep their dot as in the grid. Mood in the overview (a "Year in Pixels" lens) is left for the owner to decide.
Rejected: a fixed six-week grid (a wasted row most months); a page-height jump after the swipe; the feed's «Перейти» sheet as is (it shows only whether a month has posts, not how full it is).

## ADR-038: Links: one link, three looks; a card keeps what the page was (2026-10-19)
Owner, 2026-10-19 (plan L1-L6 in roadmap.md): a link is the `link` mark in the text or a link card, the new block `linkCard` (`href`, `title?`, `description?`, `site?`, `image?`, `view?` = `large` (default a row), `fetched?` = the day the page was read). It is an atom like `attachment`: an older client keeps it verbatim as an unknown block, so `v` stays 1. The card's picture is a JPEG blob named by its SHA-256 like an attachment's preview (uploaded and backed up the same way), not an attachment, so galleries, counts, covers and the ribbon stay the entry's own media.
A snapshot, not a cache: the page is read once, as the link goes in, never while reading (fast and private); its title, description and picture are written into the block by `_key`, an ordinary edit, so in five years the entry still says what the dead page was. A title changed by hand is never replaced. Phone and desktop read pages themselves (the server is out of reach away from home); the web asks its own server (ADR-030), which keeps the picture as a blob. Only http(s), at most 512 KB of HTML, 5 s, 5 redirects, no scripts or cookies; the server refuses addresses inside the home network, by name before each request and again as each socket connects (no DNS rebinding). Known trackers (`utm_*`, `fbclid`, `gclid`, `yclid`) are dropped as a link goes in. «Превью ссылок» can be turned off.
Opening never feels like a fall: Android opens Chrome Custom Tabs as a sheet over the entry (a swipe down and the entry is where it was; a full tab where the browser can't), desktop the system browser, the web a new tab with `noopener,noreferrer`. In the editor a tap only places the cursor and shows a bubble (open, edit, copy, unlink); Ctrl+click opens.
Removing goes down a ladder: card → link in the text → plain text → gone, each step one tap with «Вернуть». Backspace first selects an atom (a card, and since the owner asked, pictures and dividers too) and removes it on the second press.
Rejected: our own WebView (no logins, password manager or blocker, and its security would be ours); a cache keyed by URL instead of the snapshot (link rot would empty old entries); an attachment kind for the card's picture (every gallery, count and export would have to skip it).

## ADR-039: Friends: sealed letters between the owners' servers, first through a shared mailbox (2026-10-19)
Owner, 2026-10-19 (plan F1-F5 in roadmap.md): share chosen entries with a friend who runs her own Benbow server in another home, later comments and chat both ways. Each server stays single-owner; the friend is a contact, not an account: a card (an Ed25519 key that signs, an X25519 key that receives) exchanged in person and compared by its fingerprint.
Everything that goes to her is a letter: a JSON envelope signed by the sender over its HPKE ciphertext for one recipient (RFC 9180: DHKEM X25519, HKDF-SHA256, ChaCha20-Poly1305; Google Tink, no crypto of our own). Whoever carries it sees ciphertext, sizes and times; it can delay or drop a letter but can't read or forge one. Letters are numbered per contact, acknowledged, deduplicated by id and sent again when an unacknowledged one has left the mailbox, so a lost or doubled letter is harmless. Every object has one author, so nothing merges between people. The link's state is `db/peers.sqlite`, never the journal's file; it isn't backed up while it holds only test notes (F1).
Carrier (F1): one mailbox both servers log into, IMAP over TLS with an app password. A letter goes straight into the recipient's folder (APPEND: no SMTP, no spam filter, no mail between providers) and the recipient hears of it at once through IDLE. No port opens at either home, and any provider works by settings alone. Media (F5) go through Google Drive: its API if Google lets a personal app out of Testing (in 2026-10 it doesn't, and Testing's refresh tokens die in 7 days), else Drive's desktop app and a mirrored folder. Later that day the owner set the API aside (Testing's tokens make it a dead end for now) and chose the desktop app on both PCs, built early as F5a: letters still go by mail, only sealed file bodies go through Drive.
Rejected: Tailscale (its servers answer 451 to Russian addresses since 2024, and WireGuard is cut by DPI at times); a port opened to this server for now (one door to guard; kept for later, after the service leaves LocalSystem); friends as accounts on one server (permissions inside a single-owner store); merged shared entries or a CRDT (one author per object needs none); Telegram, MEGA, OneDrive (throttled or closed in Russia); the Drive API alone (Google Cloud takes no new Russian customers since 2022).

## ADR-040: The board: Keep-like notes as entries on a shelf of their own (2026-10-20)
Owner, 2026-10-20 (plan K0-K7 in roadmap.md): beside the journal, a board of notes («Записки») like Google Keep, ordered by attention rather than time: a staggered grid of cards as tall as their content, pinned ones first, dragging by finger and mouse, a choice of columns, a quick bar for a note or a checklist, an archive. Notes come and go, the journal is the life record: notes never show in the journal's feed, calendar, Home lists, look-backs, stats, tag pages, search or export, yet move both ways without copies and without fear.
A note is an entry with the LWW field `space` = `board` (no field: the journal; `space` was reserved in the protocol). It keeps everything an entry has (the Document and editor, media, drawings, links, colors, tags, revisions, diff3 merges, backups), and moving is that one field: the same id, history, media, tags, comments and day; «Вернуть» sets it back. `kind` stays (a post comes back a post). Board-only fields lie dormant in the journal: `board_rank` (a fractional string key: a move writes one field of one note, LWW), `board_pin`, `board_archived`. Into the journal a note goes on the day it was made (owner); «Другой день…» uses `when` (ADR-023). Where an entry came from (K6): a journal entry that has been on the board keeps its emptied `space` field («из записок»); a note moved from the journal carries `board_from` = `journal` («из дневника · день», and deleting it offers the journal back first).
Leak guard (ADR-027's reason for the calendar's own store): the client derives an indexed `space` column, every journal query goes through one view, and a test seeds a note and finds it in none of the journal's places; `protocol_min` rises so an older app never shows notes in its feed. Export: `export/notes/` without dates (the archive in `notes/archive/`).
UI (owner): a tab «Записки» after Календарь, Поиск moving to «Ещё» for now (six tabs are too many); a phone shows one or two columns, a card is as wide as its column, and a note opens as its card's sheet growing into the editor (no fades), for writing. Deleting is one gesture with «Вернуть» into the trash as always (no purge after 7 days); deleting a note that was a journal entry offers «Вернуть в дневник» first. No counts, badges or nudges to move anything.
Rejected: a store of its own like the calendar (notes need revisions and merges: a grocery list edited on two devices would lose one side under whole-body LWW, and moving would copy between databases and leave the history behind); a new `kind` (kind says what an entry is, space where it lives). Not planned (owner): reminders on notes, a Keep import.

## ADR-041: The media library, the storage view and purging from the trash (2026-10-20)
Owner, 2026-10-20 (plan M0-M6 in roadmap.md): one rich screen of every attachment, like a gallery; a view of what weighs what on the server, live and in the trash, heaviest first; a trash that can delete heavy media for good, behind reliable confirmations. Places (owner): «Ещё → Медиатека», an item of its own; «Место» opens from the library's header and from «Ещё → Сервер»; «Ещё → Корзина» stays.
Three steps, only the last one final: live → the trash (always restorable; now also attachments taken off an entry, `present = false`, whose files until now stayed on the server unseen) → «Удалить навсегда», only from the trash, only online, done by the server. The library and the heaviest list offer «В корзину», never a purge. «Освободить на телефоне» evicts only what the server has verified and backed up (the cache rule) and deletes nothing.
A purge is two calls, never an outbox op (nothing final may wait in a queue and fire a week later): `purge/preview` (the server counts every reference to each file and answers what frees, what stays because a live entry needs it, what hasn't arrived yet) and `purge/commit {plan_id}` (409 with a fresh preview if anything changed since). `purged` is a final state of a link, above LWW: any later put of it is absorbed; it also sets `present = false`, so older apps see it removed (an additive field, protocol 3 stays). References are counted by one function in shared/core (`MediaRefs`) over all entries: by the server for each preview, by clients for instant estimates.
Files wait 7 days in `<media>/.purged/` (owner: a quarantine), unseen by adoption, the scrub and the mirror; then they are deleted only if nothing references them by then. The admin page can undo it or free the space at once. The purge journal (an append-only file beside the DB) survives a restore and is applied again after one. The backup mirror follows (owner): it deletes its copy only by the journal, after the quarantine, hash checked. Devices delete their copies when the tombstone arrives, unless a live link there names the file.
A whole entry (owner): its files (and its comments') are purged and it leaves every device and the trash; its text stays unseen in the server's DB and snapshots (S1 untouched). Erasing text is a decision for later. Files nothing has referenced for 30 days are listed in «Место» and go the same way.
Rejected: a purge straight from the library or the feed (one tap from loss); a purge op in the outbox; deleting at once (a counting bug or a wrong tap would be final); a mirror that keeps everything (then "for good" isn't true and the second disk only grows); a reference index on the server (it could drift from the entries; a scan of one owner's entries takes well under a second).

## ADR-042: Where the server keeps things, moving them, and the app from its own server (2026-10-21)
Owner, 2026-10-21 (plan P1-P6, U1-U4, I1-I2 in roadmap.md): media off the system disk, the second disk chosen on the admin page, the library moved to a new place without a doubt; a server that can be handed to a friend; the Android app updated from its own server instead of APKs passed by hand. The owner's server had everything on one SSD and no second copy.
Folders know whose they are: `<media>/.benbow-media` and `<mirror>/.benbow-mirror` name the store. The server works only in a folder with its store's mark; a new one must be empty (or already its own), an old one is marked once when it holds files the database knows. Once the database knows files the server never makes a media folder itself (a missing disk, a letter now on another disk, someone's photo folder): without it the journal goes on, file work answers 503 (devices keep their files and retry) and nothing there is adopted, scrubbed, moved or deleted until it is back. A mirror a pass once filled is never made again either.
Moving the media copies (never moves) every file, SHA-256 checked, while the server runs; then, under a short lock, what came meanwhile, a check of the whole folder and one atomic write of `benbow.properties`. A crash at any point leaves the old folder or the new one, each complete. The old folder is never deleted on its own: after 7 days the admin page offers it, hashes checked again.
Local snapshots stay beside the database (a quick undo of a bad change); the mirror protects against a dead disk and becomes a recovery kit: snapshots, the purge journal, media, `config/` (settings, the TLS keystore), the peer identity, `export/`, a README. Restoring from it is how the server moves to a new PC (the same server, the old one stopped); a server for a friend is always a new, empty one, never a copy of a data folder. A mirror on the same volume as the database or the media is refused, on the same physical disk warned; removable disks may hold the mirror ("not connected" is a state of it), never the media.
One version for the server, the web client and the Android app; the server package carries the signed APK and the app updates itself from its server (PackageInstaller; hash, package, signature and a higher version checked first; never while recording, dictating or playing), by a tap first, quietly while closed as an option. Android and desktop clients keep a copy of their DB before migrating, as the browser does. Then a first-run page («Где хранить») and an installer over the same scripts.
Rejected: a third place for local snapshots (no new protection, one more way to go wrong); moving the data folder from the admin page (the service must be reconfigured; the DB is small); updating a friend's server from outside; deleting the old media folder by itself.

## ADR-043: An encrypted copy outside the house, by choice (2026-10-22)
Owner, 2026-10-22 (plan E0-E6 in roadmap.md, 7.7): encrypting backups is optional. Nothing changes until the owner turns on «Копия вне дома»: a folder (a cloud app's synced folder such as Google Drive or Yandex Disk, or a disk kept away from home) that gets the snapshots, the calendar, the purge journal, the media and the export, each file encrypted on its own. Only that copy is encrypted: the second disk at home stays plain, since it guards against a dead disk, restores fast and stays readable without the app (a stolen PC is BitLocker's job).
Format: age v1 (age-encryption.org, C2SP) with one X25519 recipient per store, through jagged 1.0.0 (JDK crypto only, Apache-2.0), so every file opens with the stock `age` tool and the key, without Benbow. Names in the copy say nothing: media files by a keyed hash, the export as one encrypted ZIP (its file names are titles).
The key is random and made by the server, which keeps it in the data folder and in the plain recovery kit on the second disk; daily work asks for nothing. For the day nothing at home is left, the owner chooses: a recovery code (the secret `AGE-SECRET-KEY-1…`, shown once to save or print and confirmed by typing part of it back; recommended) or a passphrase of their own (12 characters at least, typed twice; the copy then also holds `key.age`, the key sealed with age's scrypt passphrase format, so the folder and the passphrase are enough; the admin page can check it and reminds every three months). Changing the passphrase rewrites only `key.age`; the code can be shown again on the admin page in both ways. The key is made once and kept when the copy is turned off, so the code or the passphrase written down stays good for another folder too; a folder marked for another key gets nothing (one key per copy).
Verified like local backups: every file is decrypted back and compared before it takes its name; after a pass the newest snapshots are decrypted from the copy and checked (`integrity_check`), media spot-checked by SHA-256. Purges are followed as on the mirror. Restore: `restore-from-offsite.cmd` with the code or the passphrase.
Rejected: encrypting the home mirror (no protection gained, a slower restore, an export no longer readable as is); a passphrase as the files' own key (scrypt for every file: hours for the media); Tink's own formats (open only with Benbow); restic or kopia (another program to bundle and trust, their repository instead of plain files); cloud APIs (the cloud's own app syncing a folder is enough for now).

## ADR-047: The look of a note, in layers (2026-10-26)
Owner and a friend, 2026-10-26 (plan L0-L9 in roadmap.md, 7.20): each note can be made its own while keeping taste. Its look is layers over its color (`background`, ADR 6.5): paper (dots, lines, grid, parchment), a pattern (shapes, or line pictures scattered), a picture (a sticker in a corner, along an edge, or scattered), light (one to three sources: angle, tone, strength), motion (a slowly drifting gradient) and a font. Each layer is an LWW field of its own on the entry (two devices changing different layers merge), its value a token name, never a raw color or file: an unknown token draws as nothing and stays (forward-compatible like content-format's tokens); nothing in the body changes, and exports carry the fields in their front matter.
Taste by construction: patterns, pictures and light take their tones from the note's color; one pattern and one picture at most; a pattern's strength is capped so the words read. In the feed a note's look is muted (owner); motion runs only in the open note and never with the system's reduced motion; lists draw from caches, so scrolling keeps its pace. «Свой свет у каждой заметки» (a light derived from the note's id) is off by default (owner).
Pictures and textures come from free sets chosen by eye in the L0 spike: Tabler Icons (MIT, line pictures tinted to the note), Openclipart (CC0, line art for the «Бенбоу» set), Hero Patterns (CC BY 4.0: repeating tiles tinted to the note, so the app credits them where it uses them), ambientCG (CC0, paper photos blended into the note's color) and William Morris wallpapers from The Met's Open Access (CC0, faded into it). Left out: Fluent Emoji (owner), fffuel (no redistribution), Haikei and Pattern Monster output (license unclear). Fonts: eight bundled with Cyrillic (Caveat, Marck Script, Lora, PT Serif, Manrope, Rubik, Comfortaa, JetBrains Mono), more from the server's pack, the owner's own through the admin page; one font per note.
Scrapbook (owner, 2026-10-26), in three steps: first a layer drawn in code (washi tape, torn scraps, a stamp, stitches, a torn-off top), laid out from the note's id so every device draws the same, «Перемешать» keeping a new seed in its token; no files, nothing to credit. Then tape and holders on pictures (tape, a polaroid, photo corners) as a property of the picture's block, so they move with it. Stickers placed by hand last (L9): a point on the note lands elsewhere once the words reflow on another screen, so each sticker is anchored to a block by a share of its size, and is a record of its own so two devices merge.
L1 (2026-10-26): the fields are `look_paper`, `look_pattern` (own shapes, Hero tiles `hero-<name>`, Morris prints `morris-<name>`), `look_light` (its sources written out, "315 orange 2;45 blue 1", three at most), `look_motion` and `look_scrap` ("tape.7": its kind and how many times «Перемешать» laid it out anew, so the layout is the same on every device); a newer app's layers stay in their fields. Lists (feed, cards, the board, Home) draw the look muted, the open note in full, the drift only there and never with the system's reduced motion. Taste guard (owner: the busiest looked too busy): no mark of a pattern may stand more than a fixed step from the note's color, a bright tone over a far color fading more. «Оформление записки» replaces «Фон», each pick saved at once; the sets that ask for credit get it in that sheet.
Fonts (owner, 2026-10-28): one font for the whole note, words and headings alike; the journal's lists and search keep the app's own font; a text-size layer waits; handwritten diary fonts come first wherever fonts are offered. The bundled eight and the server's pack are picked on a specimen page of 57 Google Fonts with Cyrillic (all OFL) before L3 starts.
L3 (2026-10-29): the owner's eight are Neucha, Pangolin, Marmelad, Amatic SC, Cormorant Infant, Philosopher, Poiret One and JetBrains Mono (Caveat, Marck Script, Lora, PT Serif and 29 more go to the pack, L4; 16 left out). `look_font` holds the font's token; static regular and bold TTFs in the app's resources (`NoteFonts.kt`), each set at its own scale so a narrow hand reads as large as the app's font. The note's font is a composition local (`LocalNoteFont`, shared/ui) read only by the editor, the note's title, the list editor and the board's card, so bars, tags, comments and the journal's lists keep the app's font; code stays monospace. A tracker takes no font. An unknown token (a pack font not on this device yet) is the app's font.
Frames and holders on blocks and a picture grid change the content format and get ADRs of their own (L7, L8); columns start as a spike.
Rejected: a whole look as one JSON field (two devices' changes to different layers would overwrite each other); free colors and files in the fields (no taste guard, not portable).

## ADR-050: Trackers: bullet-journal sheets of one's own, kept in the calendar's store (2026-10-27)
Owner, 2026-10-27 (plan B0-B8 in roadmap.md): a section of trackers as in a bullet journal: habit trackers (the vertical one: days down the page, habits as columns with their icons), time trackers (a start/stop timer) and sheets like a sleep tracker (days × hours), each made one's own (name, emoji, colors, column texts and types) from a preset (Привычки, Вода, Чтение, Спорт, Сон, Время) or a blank sheet. Views: the month as on paper, a week strip, a year in pixels, the sleep sheet.
Model: a `tracker` record and its `column` records; a column's type says what a day's cell holds: yes/no, a number (unit, goal), a rating, a choice of one's own options (each with a color and an icon), time (spans; a timer stores only its start) or a short note. A day's value is one `cell` record with the id `<column>:<day>`, so two devices marking the same day meet in one record; a number's taps are kept per device (`add:<device>`, the total is their sum), so no +1 is lost; spans are `span` records (sleep counts for the day one wakes). Changing a column's type rewrites nothing.
Store: the calendar's (ADR-027). Values will outnumber entries and need no revisions or merges, and that file already has snapshots, the mirror, the off-site copy and the restores; the server only learns new kinds (`calendar.kinds` in `/info`, protocol unchanged). Every value a field held before it was overwritten, or that lost to a newer one, stays in the store's append-only `field_history` (every record, the calendar's too), so concurrent edits of one cell discard nothing although there are no two heads (S8). Export: `trackers/<name>/` with `tracker.json` (everything), a CSV per year and `spans.csv`, in the ZIP and the mirror.
UI (owner): a tab «Трекеры» on the web (and the desktop), «Ещё → Трекеры» on a phone; Home blocks: one leading to the trackers, one per chosen tracker (today to tick, its week or month). In the calendar only by choice: a checkbox per tracker in its sheet, off by default. Never in the feed, search, stats, tags or the journal's export.
Looks are stored as tokens only: icons `emoji:<e>` for now (hand-drawn sets later), marks in the editor's palette (`BenbowPalette`) and a mark style per column; all drawn through one look layer, so the coming redesign changes no data. An unknown token draws the default and is kept. A tracker has its own look as a note has (owner, after the spike: early, in B4): `background` and the `look_<layer>` fields of ADR-047 on its record, chosen in the same sheet («Оформление трекера»), drawn muted under the marks; the marks lie at half strength (owner: calmer).
Psychology (ux.md): totals that only count up, averages and goals, all hidden or shown with one tap per tracker; an empty cell is blank paper; no streaks, percentages, missed marks or nudges; reminders only through the opt-in reminders.
Rejected: entries (the volume, and every journal query would need a filter, cf. ADR-040's leak guard); a store of its own (a third file to thread through snapshots, the mirror, the off-site copy and every restore: one place left out is data lost in a disaster); one record per tracker and day (two devices would overwrite each other's columns).

## ADR-052: Fonts from the server: the pack and the owner's own (2026-10-29, 7.20 L4-L5)
Owner, 2026-10-28: of the 57 fonts on the specimen page, eight go into the app (L3, ADR-047), 33 into the server's pack, 16 nowhere; L4 and L5 together, handwritten fonts first everywhere.
The server offers notes fonts beyond the app's eight: the pack its package carries (`fonts/`: `pack.json` with token, name and group, `<token>.ttf` and `<token>-bold.ttf` as static TTFs from Google Fonts, their OFL texts in `licenses/`) and the owner's own, added on the admin page («Шрифты»). `GET /api/v1/fonts` lists both (token, name, group, scale, files by SHA-256 and size, whether it has Russian letters); `GET /api/v1/fonts/files/{sha256}` gives a file (immutable). A device reads the catalog after a sync every six hours and when «Шрифт» opens, keeps it with the store's id, fetches a font's files the first time it draws one, checks them by SHA-256 and keeps them (`FontShelf`: `<app files>/fonts/` on Android and desktop, IndexedDB in the browser), so a note keeps its font offline. The web takes them from its own server, like everything else.
Tokens: a pack font is its Google id (`caveat`), so one moving into the app later keeps every note; an own font is `own:<family>` (lower case, dashes), so adding its bold later keeps the notes that took it. A token the device can't draw (not fetched yet, taken off the server) is the app's font and stays in its field.
Own fonts: TTF, OTF or WOFF 1.0 (unpacked on the server, so every platform draws it as it is), one font per family, its regular and bold (weight 600 and up); WOFF2 is refused with a hint (it needs Brotli and a glyph transform the server doesn't have; Google Fonts gives TTF), as are collections (.ttc), files over 12 MB, files without a name, glyphs or a Unicode map, and an italic where the family has an upright one. The server reads the file itself (`FontFile`: tables, name, OS/2 weight and x-height, cmap coverage) and sets its size from its x-height against Roboto's (0.9-1.4; «Размер» on the page, 80-160 %). Kept in `<data>/fonts/` by SHA-256 with `fonts.json`; nothing is deleted: a replaced or removed file goes to `fonts/removed/<day>/`. The second disk's recovery kit keeps `fonts/` (and `restore-from-mirror` brings it back); the off-site copy carries it in `config.zip`.
Not sync ops: the catalog is the server's, like the app it carries (ADR-042); the notes hold only tokens. Printing and PDF carry the note's font in the page (`HtmlExporter.noteFont`, data URIs), the words and title only.
Rejected: fonts as attachments in the media store (a font isn't an entry's file: «Место» and purges would count it as one with no entry); fetching from Google at build time (the package is built offline and must not drift); WOFF2 through a JS decoder in the browser (only the browser would draw it).
