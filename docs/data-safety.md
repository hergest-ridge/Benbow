# Data safety (highest priority)

Losing or corrupting data is unacceptable from v1. Every storage, sync, migration or deletion change must keep these invariants, and tests must enforce them.

## Invariants (testable)
- **S1 Append-only content.** Entry text is never overwritten. Each save creates an immutable revision. "Restore" creates a new revision. Revisions are never deleted, except by an explicit purge (S6).
- **S2 Atomicity.** Every mutation is a single SQLite transaction that also writes its `change_log` row. There are no partial states.
- **S3 Durability.** Server SQLite runs with `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`. A write is acknowledged to a client only after it commits.
- **S4 Idempotency.** Every client op carries an `op_id`. Replays are no-ops (`applied_ops` table). Retries are always safe.
- **S5 Nothing silently dropped.** The client outbox keeps an op until the server acknowledges it. Rejected ops go to a visible "needs attention" list. They are never discarded automatically.
- **S6 Soft delete.** Deletion sets `deleted_at` (trash). Hard purge happens only by explicit user action from the trash, with confirmation, online, and only on the server (ADR-041, see "Purge"). Purged files wait 7 days in `<media>/.purged/` and are deleted only if nothing references them by then; files no entry references are never deleted directly, only listed for the owner to purge the same way.
- **S7 Verified blobs.** Uploads go to `tmp/` → fsync → SHA-256 and size check → atomic rename. Files are immutable once placed. A periodic scrub re-verifies hashes.
- **S8 Conflicts keep both.** Concurrent edits never discard either side (see `sync.md`).
- **S9 Verified backups.** A backup counts only after it has been reopened, passed `PRAGMA integrity_check` and matched row counts.
- **S10 Safe migrations.** Automatic backup before every schema migration. Migrations are forward-only and tested on fixtures. The server refuses to open a DB with a newer schema than it knows.
- **S11 Store identity.** Each data store has a `store_id` and `epoch`. Clients detect a different or restored server and never mix data blindly (see `sync.md#store-identity`).
- **S12 Drafts survive crashes.** The editor persists drafts locally on a debounce (≤500 ms) and on lifecycle stop. Killing the app loses at most the last half-second of typing.
- **S13 Format safety.** Unknown block types and fields survive every read/write byte-for-byte. A document with a newer format `v` opens read-only. Old revisions are never rewritten into a new format version (readers support every version). The codec is property-tested (content-format.md).

## Server storage layout
```
<data root>/                 (default %LOCALAPPDATA%\Benbow, user-configurable e.g. D:\Benbow)
  benbow.properties          config (host, port, TLS keystore password)
  tls/server.keystore        self-signed certificate (back it up: clients pin its fingerprint)
  db/benbow.sqlite(-wal,-shm)
  db/calendar.sqlite(-wal,-shm)   calendar store (ADR-027, 7.3a), never mixed with the journal
  db/calendar-high-water.properties   the calendar's own high-water mark
  db/purge-journal.jsonl     every purge (ADR-041), append-only, one fsync'd line each; survives a restore and is applied again after one
  db/peers.sqlite(-wal,-shm)      the link with friends' servers (ADR-039): contacts, letters, the mailbox settings; never mixed with the journal, not backed up while it holds only test notes (F1)
  peer/identity.json         the server's keys towards friends (losing it means exchanging cards again)
  peer/received/<sender>/    files friends sent (F5a test files), checked against their letters; peer/tmp/ only while sealing or opening
  tmp/uploads/               in-progress resumable uploads
  thumbs/                    derived previews (regenerable, not backed up)
  backups/db/                verified DB snapshots
  backups/calendar/          the calendar's verified snapshots and their own manifest.json
  backups/manifest.json      backup history + verification results
  backups/mirror.json        the mirror's last passes (ADR-042): its folder, when the snapshots and when everything got there
  export/                    human-readable Markdown mirror (see below)
  logs/
<media root>/                (user-chosen folder, may live inside data root)
  .benbow-media              the folder's mark (ADR-042): `store=<store id>`; the server works only in a folder that names its store
  2026/10/2026-10-12_153012_<shortid>.jpg   human-readable, immutable
  .purged/2026-10-20/...     purged files waiting out their 7 days (ADR-041), same relative paths
```
```
<backup.mirror>/             the second disk (ADR-042, as built 7.19 P2): a recovery kit for another PC
  .benbow-mirror             the mark: `store=<store id>`
  README.txt                 how to stand the server up again from here (in Russian, for the owner)
  manifest.json, db/         verified journal snapshots, purge-journal.jsonl
  calendar/                  the calendar's snapshots and their manifest
  media/                     every placed file at its path (deleted only by the purge journal)
  config/                    benbow.properties, tls/server.keystore, peer/identity.json
  export/                    the Markdown mirror as it is (follows deletions: derived)
```
Default media root: `<data>/media` (`media.root` in benbow.properties moves it, e.g. to another disk). Partial uploads live in `<media root>/.uploads` (same volume, so placement is an atomic rename) and are dropped after 7 days untouched; the device still has the original. The backup job mirrors media to `<backup.mirror>/media` (it deletes there only what the purge journal names, after the quarantine, ADR-041), re-hashes up to 200 files older than 7 days per run (mismatches are reported, never deleted), and at startup the server re-records files the database doesn't know (after a restore), never those in `.uploads` or `.purged`, nor the files a committed purge is about to move there (as built 7.18 M5: `adoptUntracked(purges.pendingPaths())` after `purges.replay()` at every start).
**Marks (ADR-042, as built 7.19 P1).** `<media>/.benbow-media` and `<mirror>/.benbow-mirror` name the store (`store=<id>`, written atomically). The media folder is used only while its mark names this store: a folder of another store, or one that is neither empty nor holding a file the database knows (someone's photo folder), is refused, and nothing in it is ever adopted (so nothing there can become «Без записи» and be purged). A folder without a mark is marked once when it is empty and the database knows no files, or when it holds a file the database knows at its path with its size (folders from before 7.19). Once the database knows files the server never makes the media folder itself: when it is gone (a disk unplugged, its letter on another disk, an empty folder of that name) the journal goes on and file work answers 503 `media_unavailable` (uploads, chunks, downloads of known files, purge preview and commit; devices keep their files and try again), while adoption, the scrub, dropping stale uploads, the quarantine's moves and its end, undo and «Освободить сейчас» wait, marking nothing. It is usable again by itself when the folder is back. Folders under the root are made one level at a time (`createUnder`), so a root that vanished fails instead of coming back empty. The mirror's rules are under "Second location" below.
Media paths are human-readable on purpose: if the app ever dies, the files can still be browsed. Dedup works by SHA-256 in the DB (the same hash reuses the existing file).

## Backups
- **DB snapshots** via the SQLite online backup API or `VACUUM INTO` into `backups/db/benbow-YYYYMMDD-HHMMSS.sqlite`. Triggers: hourly while there have been changes, daily, before migrations and updates, and on demand.
- **Retention (GFS):** 24 hourly, 14 daily, 8 weekly, 12 monthly, plus all pre-migration snapshots for 90 days.
- **Second location:** a second local disk (owner's choice, ADR-010). It gets copied DB snapshots plus an incremental media mirror (immutable files, so copying by hash is enough). Warn loudly if the target disk is missing or full. Cloud targets come later, and they must be encrypted. As built 7.19 P1 (ADR-042): a pass writes only into a folder whose `.benbow-mirror` names this store, and marks one that is empty or that this store filled before (a snapshot of the same name and size, a media file it knows); a folder of other things or of another store gets nothing. A folder a pass once filled (`backups/mirror.json`) is never made again when it is gone: the pass skips it, the snapshots are still taken here, and the admin page says why. Without the media folder the snapshots still go to the mirror, the media wait, and the mirror deletes nothing by the purge journal. `mirror.json` keeps the last passes across restarts. As built P2: a folder on the same volume as the database or the media folder gets nothing (no protection against a dead disk); each pass also copies the recovery kit (`config/` with the settings, the TLS keystore and the peer identity; `export/` as it is, the only part of the mirror that follows deletions, being derived; a README), every file through a temporary file checked by SHA-256 and only when it changed. Warnings that don't stop a pass: under 5 GB free there, a partition of the same physical disk as the database or the media (`Get-Partition`). The admin page says loudly when there is no second disk at all and when the last full copy is over 48 hours old. `peers.sqlite` is still not in it (F1 holds only test notes). As built P3: the admin page's «Второй диск» chooses the folder (the server's folder picker, Drive's group hidden there) and checks it before anything is saved (`MirrorChoice`): a full path to a folder, not a whole disk; local, not a network share; not Drive's streaming disk; NTFS, ReFS or exFAT; not inside the data or media folder nor holding one; not on their volume; empty or this store's mirror already; room for the media, the snapshots and the export plus 1 GB unless it is this store's already; a test file written, synced, read back and removed by the server itself (a folder made for the check is removed again when it fails). Saving marks the folder, writes `backup.mirror` in one atomic step (`ServerConfig.update`) and switches without a restart: a pass under way finishes with the folder it began with, and what it found is not shown for the new one; the first pass starts in the background with its progress on the page. Another folder leaves the old one as it is; «Отключить» (confirmed) stops the copies and leaves the folder too. «Сделать копию сейчас» runs in the background as well.
- **Export mirror:** periodic export of every entry to `export/YYYY/MM/YYYY-MM-DD HHmm <title>.md` (rich Markdown with YAML front matter: id, kind, day, tags, mood, favorite, attachments as relative links) **plus** a `.json` sidecar with the canonical Document and metadata (lossless). This is the disaster-recovery format that needs no app. Optionally a local git repo for free history. Tags list as they read (ADR-032: the registry's names, merged tags as their target, none from the trash; the sidecar also has `tags: [{id, name}]` and, as always, the raw `tag:` fields); the server keeps the registry's names, merges and trash it last wrote in `export/.tags.json` and writes again every note of a tag that reads differently. Notes on the board (ADR-040) go to `export/notes/` (their archive to `export/notes/archive/`), named by day and id like the rest; when an entry moves between the journal, the board and its archive, the mirror writes it at its new place first and then removes the copy from the old one, so it holds every entry once. Beside the notes, `export/tags.md` (to read) and `export/tags.json` (for programs, `benbow-tags/1`) list every tag and category with names, categories, descriptions, colors, emoji, the archive, merges and the trash (`TagBook` in shared/core, 7.9 T5); they are written again whenever the registry changes.
- **Archive export from the app** (6.3): "Ещё → Экспорт" writes one ZIP wherever the user picks: `entries/YYYY/MM/` (board notes in `entries/notes/` and `entries/notes/archive/`) in exactly the mirror's format (`EntryExport` in shared/core, used by both), `tags.md` and `tags.json` as in the mirror (7.9 T5), the files under `media/YYYY/MM/` (original names, de-duplicated by hash), and a README with counts. Left-over drafts are committed first. Files not on the device are fetched from the server; any that can't be are named in the README and as a comment in the note, never dropped silently. A purged file (ADR-041) is named the same way, as «файл удалён навсегда <date>», in the ZIP and in the mirror. Read-only otherwise.
- **Status visible:** the admin page and the client settings show last backup time, last verification, and last mirror sync. The UI warns if the latest backup is older than 48 hours.
- **Calendar (ADR-027, 7.3a):** `calendar.sqlite` gets its own snapshots in `backups/calendar/` (`calendar-YYYYMMDD-HHMMSS-<reason>.sqlite` and a manifest of their own) with the same verification (S9), GFS retention, pre-migration and pre-update snapshots, and a copy to `<backup.mirror>/calendar/`. It runs as a step of its own after the journal's: its failure shows apart on the admin page and never stops or fails the journal's snapshot. The mirror (`export/calendars/`, rewritten whole when the calendar's epoch or change log moved, after each calendar pass) and the app's ZIP (`calendars/`) get `<name>.ics`, one file per calendar with what it shows, readable by any calendar app (ADR-028), plus `calendar.json` with every calendar and event record as stored, deleted ones included (as built 7.3c).

Implemented (server 0.2.0): `Backups` (VACUUM INTO + reopen + integrity_check + row-count match, manifest.json), `BackupJobs` (snapshot on change every `backup.intervalMinutes`, `Retention` GFS pruning, verified SHA-256 copy to `backup.mirror`, Markdown mirror in `<data>/export`), pre-migration and pre-update snapshots in `Database.open`, revisions protected by SQLite triggers (no UPDATE/DELETE). Config paths in `benbow.properties` must use `/` (Java properties treat `\` as an escape); a relative mirror path is rejected.

## Purge (ADR-041, as built 7.18 M5, server 0.12.0)
Before 7.18 nothing was ever deleted: an attachment taken off an entry (`present = false`) and the files of trashed entries stay on the server. The purge is the only way a file leaves, and it is built so that a wrong tap, a counting bug, a late op or a restore can't take a file a live entry needs.
- **Only from the trash, only online, only the server.** Live media can go to the trash (restorable); «Удалить навсегда» exists only there. It is two calls, never an outbox op: `purge/preview` returns what the server would delete and a `plan_id` tied to its change-log cursor; `purge/commit` counts again with the database's lock held and applies exactly that plan, or nothing: 409 `changed` (the device previews again and shows the new count), 410 `expired` (ten minutes), 400 `not_in_trash`. The commit is one transaction: links become `purged`, the change log, the purge journal line (fsync'd before the answer), the queue of file moves.
- **References.** A file is referenced by every link that isn't purged (live, `present = false`, or in a trashed entry), through its `sha256` and `preview_sha256`, and by every SHA-256 an entry's head and conflict heads name (`linkCard.image` today; the text is scanned for runs of exactly 64 lowercase hex digits rather than decoded, so a block a later app adds or a body this build can't read still holds its files: counting too much only keeps a file). A comment shares the trash of the entry it answers, at any depth. `MediaRefs` in shared/core computes them over all entries (as built 7.18 M1: `plan(PurgeSelection)` answers `Refused` for anything not in the trash, an unknown entry or link, or an "unreferenced" file something holds, else `Ready` with the entries leaving, the links becoming purged, the files deleted and those staying with what keeps them); the server will scan for every preview (no index to drift). A plan never names a file a remaining reference holds: it is listed as staying, with the entries that keep it. An entry's purge takes its comments with it. `MediaRefsTest` checks over 2,000 random worlds (shared files, previews, comments, cards, removed and purged links) that after a plan the held files are exactly those before minus the plan's files.
- **Tombstone.** `purged` is final: a later `entry.attachment.put` of that link (an offline device's «Вернуть», a clock ahead) is absorbed as applied and changes nothing. The server sets `present = false` too, for older apps.
- **Quarantine.** After the commit, files move to `<media>/.purged/<day>/` (a queue row each, so a crash mid-move resumes; moving is idempotent). Adoption, the scrub and the mirror never look there; devices can't fetch from there. After 7 days a file is deleted only if, at that moment, no reference names its hash (the same photo attached again keeps it, moved back). The admin page can undo a purge within the 7 days (the only way out of `purged`: links back as they were with a fresh HLC, files back, an undo line in the journal) or free the space at once (a second confirmation there).
- **Uploads.** Starting an upload of a file whose every link is purged answers 410 `purged` (the device skips it, not a failure, and lets its copy go once the purge is pulled). As built, an upload already under way that completes after the commit is placed like any file and, held by nothing, shows in «Место» as «Без записи» (purged the same way); nothing is deleted on its own.
- **Journal.** `db/purge-journal.jsonl`: one line per commit (time, device, the links with their states before, the files with their paths, sizes and names), appended and fsync'd after the commit and before the answer, copied to `<backup.mirror>/db/` in every backup pass; the `purges` table holds the same lines (server schema 4, with `purged_files`, the queue of each file: `moved_at`, `deleted_at`, `back_at`, `mirror_deleted_at`). A crash between the commit and the line is mended at the next start (`replay` writes the lines the journal lacks). After a restore (new epoch) the server applies every line again before serving, so an older snapshot can't bring back links to deleted files; devices re-pushing their tombstones agree with it.
- **Mirror.** `<backup.mirror>/media` deletes a file only when the journal names it, its quarantine has ended and its hash matches; a file the journal doesn't name is never deleted there.
- **Devices.** When a purged link arrives, a device deletes its copy (captured or downloaded, IndexedDB on the web) unless a link on the device that isn't purged, a live entry's text or a draft names the same hash (`purgedMedia`, `dropPurged` before each round of uploads). `forgetPurged` is the one query that drops a captured file's row before the server verified it; nothing else does.
- **Whole entries.** Their files go as above and the entry (the field `purged`, written only by the server: a device's write of it is absorbed) leaves every device and the trash: the client's `journal_entry` and `board_entry` views and the ZIP export leave it out; its revisions stay in the server's DB and snapshots, unseen (S1 holds), and its text no longer holds any file. A link put on it later is purged from the start. The Markdown mirror and the ZIP name a purged file in a comment (`<!-- video VID.mp4 deleted for good -->`), never a dead link.
- **Unreferenced files** (no reference for 30 days: a file may arrive before its link) are listed in «Место» and purged the same way, never automatically. As built (M6): `GET /api/v1/storage/unreferenced` lists the blobs nothing holds that were placed 30 days ago or more (their `created_at`), the heaviest first; a preview naming a younger one is refused (`too_new`), and one something holds is refused (`referenced`).
- Tests (as built): `MediaRefsTest` (plans over random worlds); `TombstoneSimulation` in shared/testing, run by `PurgingTest` on the in-memory store and by `PurgeTest` on SQLite (offline devices taking off and bringing back links while answers get lost and the server purges: a purged link never comes back, every device ends with the server's links); `PurgeTest` drills: a commit doing exactly its plan, a plan that changed (the same file attached to a live entry meanwhile), a late «Вернуть» absorbed and the upload refused, the quarantine's end (deleted, or back when attached again), the undo, a restore to a snapshot from before the purge (done again from the journal, nothing adopted from the quarantine), a crash before the files moved, the mirror (only by the journal, after the week, the hash matching); `PurgeApiTest` over HTTP; `PurgedOnDeviceTest` (copies, the trash, the upload queue); `TrashPurgeTest` (a tap does nothing, a held button deletes, a changed plan recounts, offline can't).

## Moving the media (ADR-042, as built 7.19 P4)
The media folder moves by copy, never by moving files (`MediaMove`, state in `db/media-move.json`).
- **Check first.** The media folder must be there; the new place is a full path to a folder (not a whole disk), local (not a network share, not Drive's streaming disk), NTFS or ReFS (exFAT has no journal), not inside the media folder, the data folder or the mirror nor holding one, not on the mirror's volume (the media and their copy on one disk), empty or a folder a move of this store was filling (`.benbow-moving`), with room for what is still to copy plus 1 GB, and writable by the server itself (the write probe). Nothing starts when it fails.
- **Copy while serving.** Every file of the old folder (the quarantine included, uploads in progress not) goes through a temporary file synced to disk (`force`) and read back for its SHA-256, then an atomic rename; a file whose bytes don't match the database's hash is copied as it is and logged (the scrub reports it). Uploads, purges and the backup pass go on in the old folder meanwhile.
- **The switch, all file work held off.** `BlobStore` runs file work under a shared lock (`withFiles`: uploads, placing, dropping stale uploads, adoption, the quarantine's moves, its end and undo); the switch holds it exclusively (`switching`) for a moment: it copies what changed since (new files, files gone to the quarantine, every upload in progress), removes from the copy what left the old folder (a file staying at its old place would come back as one the database doesn't know), checks that every file of the old folder and every file the database knows there is in the new one with its size, writes the new folder's `.benbow-media`, writes `media.root` in one atomic step (`ServerConfig.update`) and only then points the server at it. The media lock is always taken before the database's.
- **Crashes.** Before the settings change they name the old folder (complete; the copy goes on at the next start, `resume`); after, the new one (complete; the next start finishes the bookkeeping). A move stopped by an error (a disk gone, full) waits for the owner: try again (`retry`) or cancel; cancelling deletes nothing.
- **The old folder** is left as it was, its mark saying `moved-to=<new folder>`, so the server never takes it for the media folder again (`MediaFolder.State.Moved`); the move is listed in `media-move.json` under `left`. As built P6 (`LeftFolders`): for a week it is a spare copy and nothing can delete it; then «Проверить и удалить…» checks it and «Удалить старую папку» (confirmed) checks it again right before deleting. A file may go only when the media folder now holds the same bytes at the same place (SHA-256 of both) or when the purges' records name it (deleted for good by the owner); parts of uploads the move carried on go too. One file that doesn't check stops it all and nothing is deleted. Only a folder whose mark says it is this store's and moved, never one that is or holds the media folder, the data folder or the mirror, nor one inside the mirror; only paths on the `left` list are acted on. Files go first, then folders, the mark and the folder last, so a stop halfway leaves it marked. A folder already gone can be taken off the list. No move may go into a left folder (deleting it would take the media along). The Markdown mirror is written again whole at the next pass (its links name the files' places).
- **On the admin page (P5):** «Копии → Медиафайлы» shows the folder, its files and the room on its disk; «Перенести в другую папку» first only looks (`preview`: the same checks, nothing made) and shows how many files and gigabytes go where and what is free there; only «Начать перенос» starts. The live part shows the copy's progress, a stop with its reason and «Продолжить» / «Отменить перенос» (confirmed), and every folder a move left behind.
- Tests: `LeftFolderTest` (the week, an intact folder deleted with the media untouched, a damaged or missing copy keeping the whole folder, a file deleted for good, a folder without the moved mark, no move into a left folder, a gone folder forgotten, the admin page's wait, check and delete); `MediaMoveAdminTest` (the look before the move, a refusal, the move; a stop, cancel, the same folder again, «Продолжить»); `MediaMoveTest` (a move with an upload under way, every refusal, an upload and a purge between the copy and the switch, a crash at each step followed by a start, the new disk gone and back, a full disk, a cancel, a restore after the move).

## Integrity checks
- On startup: `PRAGMA quick_check`. Nightly: `PRAGMA integrity_check` + `foreign_key_check` + a blob scrub over a rolling subset (all files over 7 days).
- On failure: switch to read-only mode, alert in admin page and clients, keep serving reads. Never auto-repair destructively.

## Migrations
- Schema versioned with SQLDelight `.sqm` files plus `verifyMigrations`. `PRAGMA user_version` is tracked.
- Startup sequence: detect pending migration → snapshot backup (verified) → migrate in a transaction → integrity check → serve.
- Fixture DBs for every released schema version live in tests. Each must migrate to latest with identical content checksums.

## Client-side safety
- The local DB is a cache + outbox + drafts. The outbox is the only client-owned data, and it is deleted only after the server acknowledges it.
- Captured media is copied into app-private storage immediately, so deleting the source in the gallery can't lose it. The local copy is evicted only after upload is confirmed (and, if available, after the server reports it as backed up). As built: a captured file may be evicted only 7 days after the server verified it (the backup job runs hourly), and only when the media cache is over its cap. «Освободить на телефоне» (ADR-041, planned) evicts under the same rule below the cap and deletes nothing the server lacks; a purged file is deleted from devices as in "Purge".
- Dictation takes (7.10, ADR-033) are written to `capture/dictation-<time>.wav` as they're recorded (each chunk reaches the system at once; the header and an fsync come at the end), with the entry id in a `.entry` file beside. A take that fails to become text, or whose screen went away first, becomes a voice note of its entry (or of a new note); takes a dead process left behind become voice notes on the next start, read to the end of the file whatever the header says. A take whose text is in is renamed `.done.wav` and waits only for «Приложить запись» while that message shows; those are dropped on start.
- The local DB runs WAL + `synchronous=FULL` (drafts and the outbox exist nowhere else). The device token is sealed with a key in the Android Keystore.
- **App updates from the server (ADR-042, as built 7.19 U2).** A sync keeps what app the server offers (`Settings.serverApp`, from `info.android`, even when the protocol no longer fits). Only this app (the same package id: a dev build never takes the owner's app) and a newer `versionCode` is fetched (`AppDownload`: resumed after cuts, size and SHA-256 as the server said, a file that doesn't match deleted), then checked by Android's package manager before anything else: this package, signed by the same certificate, newer; else it is deleted. It is installed only on the owner's tap («Ещё → Обновить»), never while a voice note is recorded, a dictation runs or a sound plays, through one PackageInstaller session (`USER_ACTION_NOT_REQUIRED`: Android may skip its own dialog). The process ends with the update; drafts are on disk within 500 ms (S12) and the outbox in the DB, so nothing waits in memory. A refusal comes back as the line's error, with «попробовать ещё раз». Play Protect may ask to scan an app it hasn't seen («Install without scanning» under «More details» keeps the APK on the device).
- Exclude the DB from Android Auto Backup. Restoring a stale cache onto a new phone would confuse sync. Device recovery happens through a fresh pull.
- Every device cache doubles as a partial backup. After a server restore, clients can re-upload what the server lacks (see `sync.md`).

### Browser client (ADR-029, W1-W3)
The browser has no fsync'd files; its lasting storage is IndexedDB of the page's origin. How the same guarantees hold there:
- **DB (S2, S3):** SQLite (sql.js) runs in the tab's memory; the whole file is put to IndexedDB after 1 s without changes (at most 5 s while changes keep coming), as one atomic put flushed with `durability: 'strict'`, so the stored file is always a complete snapshot. A snapshot never ends a transaction (it waits for none to be open). Typing reaches the DB within 400 ms (`DraftSession`).
- **Closing or hiding the tab:** on `visibilitychange: hidden` open drafts become revisions and both DBs are flushed; `beforeunload` asks ("Leave site?") while typing, a DB snapshot or a media file is still on its way, and starts saving at once, so it is done before the user can answer. Only a browser or OS crash can lose the last few seconds.
- **Media (S3, S7):** a picked, dropped or pasted file is stored as a Blob in IndexedDB (`media/<sha256>`, SHA-256 by WebCrypto) before the entry refers to it, uploaded from the stored blob in slices, and kept by the same rule as the apps (7 days after the server verified it, only over the cap). Downloads are verified against their hash before they are kept.
- **One owner:** one tab holds the data (Web Locks); a second tab of the same origin refuses to open it, since two in-memory copies would overwrite each other's snapshots.
- **Migrations (S10) and damage:** the old file is kept beside the new one (`<name>.before-v<N>-<time>`) before migrating; a file that fails `quick_check` is kept aside (`<name>.damaged-<time>`), never deleted, and an empty DB fills again from the server.
- **Export (W5):** "Ещё → Экспорт" works in the browser too: the same `ArchiveExport` (now common code behind `ArchiveWriter`) builds the ZIP from parts, the media as the Blobs from IndexedDB (never read whole into memory; CRC-32 read in slices), ZIP64 where sizes need it, and hands it to the browser's downloads.
- Covered by `shared/client` wasm tests in Node (`BrowserSqlDriverTest`, `BrowserMediaTest`, `ZipTest`, with an in-memory shelf).

## Calendar store (ADR-027, 7.3a)
Events matter less than entries and will outnumber them, so they live in their own files (server `calendar.sqlite`, client `calendar.db`) and calendar code never opens the journal DB. The one exception is moving the 5.1 events (`moveJournalEvents`, on every start, idempotent): it reads them and only trashes the old entries (soft delete).
- The calendar file carries the journal's store id; a file of another store is refused. If it doesn't open (corrupt, another store's), the server logs it, the admin page says so and the journal runs as usual.
- Kept: S2 atomicity, S3 durability (WAL + `synchronous=FULL` on both sides, since the outbox lives only there), S4 idempotency, S5 nothing silently dropped, S6 soft delete (calendar trash, explicit purge), S9 verified backups, S10 safe migrations (own `user_version`, snapshot before migrating), S11 (own epoch), unknown fields survive.
- Not applied: S1 and S8. Fields are LWW without revisions, so concurrent offline edits of the same field keep the later one. That is acceptable for events, and an imported calendar can always be imported again from its file.
- The client's `calendar.db` is excluded from Android Auto Backup like the journal DB.
- Imports (7.3d) read the whole file before writing anything (a file over 100 MB or a ZIP unpacking past 200 MB is refused), write only into the calendar's file, 500 records to a transaction with one op each, and "Отменить импорт" moves the batch's events and the calendars it made to the trash (soft delete, restorable).

## Disaster recovery runbook
1. Server DB corrupt or a bad change → run `restore-backup.cmd` as Administrator (default: newest verified snapshot; or `restore-backup.cmd <file>`; snapshots from the mirror work too). It stops the service, moves the current DB to `<data>/db/replaced-<time>` (nothing is deleted), puts the snapshot in place with a new epoch and starts the service. Paired devices see the new epoch and reconcile: they re-upload entries, head revisions and field values the snapshot lacks; a lost edit of an entry that exists in the snapshot comes back as a second head (conflict) for the user to pick. Copying a snapshot by hand also works: `db/high-water.properties` lets the server notice the regression at startup and bump the epoch itself.
2. PC dead → on the new PC, from the server package, as Administrator: `restore-from-mirror.cmd <mirror> [data folder] [media folder]` (`--restore-from-mirror`, `MirrorRestore`), then `install-service.cmd [data folder]`. It only reads the mirror and goes only into a data folder with no database and an empty media folder: the settings (now naming this mirror and this media folder), the TLS keystore (devices know the server by the same certificate) and the peer identity; every snapshot with its manifest (so the next pass doesn't prune the mirror's history) and the newest verified one in place with a new epoch, the calendar likewise; the purge journal (done again at the first start); every media file copied and checked by SHA-256, the folder marked. Devices see the new epoch and re-upload what the snapshot lacks; the old server must be off for good. A mirror written before 0.12.1 has no `config/`: then install fresh, put a snapshot back with `restore-backup.cmd <file>` and re-pair the devices.
3. App unusable → the Markdown mirror plus the media folder are readable as plain files.
4. Calendar file corrupt or a bad calendar change → run `restore-calendar.cmd` as Administrator (`--restore-calendar latest|<file>`): only `calendar.sqlite` goes back (the replaced one moves to `db/replaced-<time>`), the journal stays as it is. The calendar epoch goes up and devices re-push what they have. Last resort: import the calendars again from their `.ics` files (7.3d).
