# Architecture (proposed, pending confirmation, see decisions.md)

## Stack summary
| Layer | Choice | Why |
|---|---|---|
| Language | Kotlin 2.4 everywhere (clients and server) | One language and shared types: models, content codec, sync and merge logic, API DTOs. Less AI context |
| UI | Compose Multiplatform 1.12.x: Android, Desktop (JVM), Web (wasmJs) | One UI codebase for three targets. Android is the primary target. Web is Beta (see research.md) |
| Design | Material 3 + Expressive APIs (experimental opt-in), wrapped in our own `BenbowTheme` tokens | Expressive is still alpha in CMP. Our wrapper absorbs API churn |
| Content | Benbow Document v1 = Portable Text-based JSON (content-format.md), exporters to MD/HTML/text/PDF | Rich formatting, lossless 1:1 storage, stable block keys |
| Client DB | SQLite via SQLDelight 2.x (Android and JVM) | SQL-first and transparent. Migrations verified by tooling. FTS5 |
| Web client | The same app compiled to wasmJs, served by the server (ADR-029) | Same screens and client as Android/desktop; local SQLite via sql.js, saved to IndexedDB |
| Server | Ktor 3.x on JVM, SQLite (xerial sqlite-jdbc) via SQLDelight | Shares code with clients. Stable and well known |
| Packaging | jlink runtime (Temurin 25 LTS) + jars + WinSW Windows service running `runtime\bin\java.exe` | Standalone, autostart, auto-restart, no Docker. GraalVM native-image is a possible later optimization |
| API | REST + JSON under `/api/v1`, OpenAPI generated by the Ktor plugin, docs page at `/api/docs` | Versioned, documented, Monbooru-style built-in docs |
| Sync | Outbox of idempotent ops + append-only revision DAG + server-side 3-way merge, LWW (HLC) for metadata | Never loses data, debuggable, no CRDT dependency (see sync.md) |

## Runtime topology
```
[Android app]  offline cache + outbox ──HTTPS(LAN) /api/v1──┐
[Desktop app]  offline cache + outbox ──localhost / LAN─────┤
[Browser]      same app (wasm), sql.js DB in IndexedDB ─────┤
                                                            ▼
                         benbow-server (Windows service, Ktor/JVM)
                         ├─ <data>/db/benbow.sqlite   (WAL, synchronous=FULL)
                         ├─ <data>/db/calendar.sqlite (the calendar's own store, ADR-027)
                         ├─ <media root>/YYYY/MM/...  (user-chosen folder, immutable files)
                         ├─ <data>/backups/           (verified snapshots, GFS retention)
                         ├─ <backup target>/          (second disk / NAS / cloud folder mirror)
                         ├─ <data>/export/            (human-readable Markdown mirror)
                         └─ admin page "/", API docs "/api/docs", web app "/app"
```
The server being unreachable is normal: clients keep working and sync later.

## Module layout (start small, split when a module exceeds ~15k LOC or build times hurt)
Scaffolded so far: `shared/core`, `shared/ui`, `shared/client`, `shared/app`, `shared/testing`, `apps/{android,desktop,web}`, `server`. `build-logic/` arrives only once duplication between build scripts starts to hurt.
JVM toolchain 17 for all modules (foojay auto-provisioning). Namespace `app.benbow`.
```
build-logic/        Gradle convention plugins (later)
gradle/libs.versions.toml
shared/core/        KMP, all targets incl. server JVM. Pure Kotlin: ids (UUIDv7), time/day logic, domain
                    model, Document codec + canonicalizer + exporters/importers, sync protocol DTOs, diff3 merge, HLC, validation
shared/client/      KMP android/jvm/wasm: SQLDelight cache + drafts + outbox, JournalRepository, DraftSession,
                    SyncEngine + SyncController, pairing, pinned-TLS Ktor/OkHttp API client (fetch in the browser);
                    JVM-only pieces (MediaStore, archive export, speech model) in src/jvmShared, the browser's
                    (BrowserSqlDriver over sql.js, BrowserShelf = IndexedDB, BrowserMedia) in wasmJsMain
shared/ui/          CMP android/jvm/wasm: BenbowTheme/design system, editor
shared/app/         CMP android/jvm/wasm: screens, navigation, ViewModels, AppServices
shared/testing/     sync simulation + in-memory store shared by core, client and server tests
apps/android/       Android entry, platform services (WorkManager, notifications, media capture, widgets,
                    QS tile, share target), baseline profiles
apps/desktop/       Compose Desktop entry + MSI packaging
apps/web/           wasmJs entry: opens the browser's DBs, boots shared/app. Build output is embedded into the server distribution
server/             Ktor app: routes, storage, blob store, backups, mirror export, admin page, packaging
docs/
```
Dependency rule: `apps/{android,desktop,web} → shared/app → shared/{ui,client} → shared/core`; `server → shared/core`. Nothing depends on apps.

## Client architecture
- Unidirectional data flow: ViewModel (androidx lifecycle KMP) exposes `StateFlow<UiState>`. UI sends intents. Repositories are the single source of truth backed by the local DB (Flow queries).
- Optimistic local writes: write to the DB and outbox in one transaction, update the UI instantly, then the sync engine pushes in the background.
- DI: a plain `AppServices` object created by the platform app (enough for one process-wide graph; Koin if it grows). Navigation: Navigation 3 with a ViewModel store per entry. Images: Coil 3.
- Editor screen: typing goes to a `DraftSession` (draft within 400 ms, revision after 30 s idle / 2 min typing / leaving / app stop). Text arriving from sync or a restored version replaces the editor content only if the user hasn't typed since it was loaded or last committed.
- UI smoke test: `shared/app` jvmTest drives the whole app headless and writes screenshots to `shared/app/build/screens`.
- Sounds (7.12, ADR-035): `TrackReader` in `shared/core` (`app.benbow.core.audio`) reads ID3v1/v2, MP4, FLAC, Ogg, WAV and AIFF tags, covers and lengths from any `RandomRead` (a stored file read in pieces: `LocalFile.randomRead()`). `AudioPlayer` (common, one per process in `AppServices`) keeps the queue and drives a platform `AudioEngine`: `AndroidAudio` (one ExoPlayer, audio focus, `PlaybackService`: a not-exported media3-session `MediaSessionService` whose `ForwardingPlayer` sends next / previous to the queue), `JavaFxAudio` on desktop (OpenJFX 21 media for the build machine's OS; mp3, m4a, wav and aiff through a named temp copy, the rest to the system player), `BrowserAudio` (the page's `<audio>` and the Media Session API). `MiniPlayer` and `PlayerScreen` (colors from the cover via materialkolor) live in `shared/app`.
- Media UI (3.3): common gallery strip, journal covers, full-screen viewer (pinch/double-tap zoom) with Coil 3; `MediaBar` and `MediaPlayer` are expect/actual. Android: Photo Picker (no permission), camera via `TakePicture` into `files/capture` through a FileProvider (the temp file is deleted only after a successful import), hold-to-record voice (AAC .m4a, `RECORD_AUDIO`), previews from EXIF-rotated bitmaps and video frames, playback with Media3 `PlayerView`. Desktop: file dialog, ImageIO previews, video/audio opened in the system player. Modules whose targets are all JVM (android + jvm) may use JDK APIs in commonMain.
- Search (4.1): on-device SQLite FTS4 (`entry_search`, Android has no FTS5) over title, all text and tags, `unicode61` (case-insensitive) plus our own ё→е folding; every typed word is a prefix query, non-letters are dropped so FTS syntax can't be injected. Updated in the same transaction as the entry; rebuilt when `SearchIndex.VERSION` changes. Filters: tag (JSON path on fields), favorites, with media. Server-side FTS waits for the web client.
- Performance: immutable UI models, stable keys and `contentType` in lazy lists, paging by cursor, prefetch of adjacent entries, baseline profile (`apps/android/src/main/baseline-prof.txt`, installed by profileinstaller), R8 without obfuscation (ADR-024), a cache window on the feed. The feed reads an index of every post and the posts in full in windows around the screen (ADR-036).

## Server internals
- Single write connection (serialized writer) + read pool, like Monbooru. All mutations are transactional and append `change_log` rows in the same transaction.
- Services: `SyncService` (push/pull), `BlobStore` (resumable upload, verify, place), `RevisionService` (DAG, merge), `BackupService` (scheduler, verify, retention, mirror), `ExportService` (Markdown mirror, ZIP export), `SearchService` (FTS5), `PairingService`.
- Admin page: server-rendered HTML (kotlinx.html), independent of the wasm app so it keeps working if the web client breaks. Shows status, last backup, integrity, devices, pairing QR, "backup now".
- Config: `<data>/benbow.properties` (created with defaults: host, port 8765, TLS keystore password). Logs: `<data>/logs/`, daily rotation. `<data>/tls/server.keystore`: self-signed certificate. `<data>/.lock`: one server per data dir.

## Packaging and deployment (Windows)
1. `./gradlew :server:packageServer` → `server/build/package/benbow-server/`: `runtime/` (jlink, ~52 MB, modules from jdeps), `lib/` (jars), scripts. jpackage isn't needed: WinSW starts `runtime\bin\java.exe` directly.
2. Bundle WinSW (`benbow-server-service.exe` + `.xml`): auto start (delayed), restart on failure, log rotation. The JVM gets `-Xmx1g` (since 7.7 E4: scrypt for the off-site copy's passphrase takes 256 MiB); setup.exe writes the service config again on an update, update-service.cmd keeps the old one.
3. `install-service.cmd [data dir]` (admin): registers the service, opens TCP 8765 for private networks, starts it. Default data dir `%ProgramData%\Benbow`. As built 7.19 (ADR-042): the media folder and the mirror are chosen on the admin page, «Где хранить» (I1) shows where everything is and what would be better. I2: `./gradlew :server:installer` makes `server/build/installer/benbow-server-setup-<version>.exe` with Inno Setup 6 (`packaging/installer/benbow-server.iss`, Russian only; ISCC looked for in the per-user and all-users places, or `-Pinnosetup.iscc`; not part of `check`). It does what the scripts do, in the same places: the program in `%ProgramFiles%\Benbow Server`, the service `BenbowServer` from the template, the firewall rule. A new install asks for the data folder (empty, new, or one with Benbow's data; a local fixed disk; never inside the program folder); an update (the service exists, from that folder) stops it, waits for Java to let go, replaces `lib`, `runtime`, `web`, `android` whole, writes the service config again with the same data folder and starts it; an older setup over a newer `version.txt` is refused (the server would refuse the newer schema anyway). Removal takes the service, the rule and the program away and leaves the data folder. An entry in «Программы и компоненты», a Start menu link to the admin page. The setup is unsigned: SmartScreen asks once («Подробнее» → «Выполнить в любом случае»). `benbow.ico` is the app icon (favicon.svg) drawn by headless Edge at 16-256 px; draw it again when the icon changes.
4. Updates: stop service → automatic DB backup → replace app-image → start → migrations run (see data-safety.md).
One version (ADR-042, as built 7.19 U1): `benbow.version` in `gradle.properties` is the server's `SERVER_VERSION` (generated `Version.kt`), the web client it carries and the Android app's `versionName`; the app's `versionCode` is `major * 1,000,000 + minor * 1,000 + patch` (0.13.0 → 13000), so it grows with every release. `packageServer` also builds the signed release app (`:server:androidRelease` → `:apps:android:assembleRelease`) into `android/`: `benbow-<version>.apk` and `release.json` (`version_code`, `version_name`, `file`, `sha256`, `size`, read from the build's own `output-metadata.json`). The server checks the APK against it at start (`AppRelease`) and offers it to phones; the release key in `%USERPROFILE%\.benbow` now signs every update phones take from their server, so it needs a copy kept apart. `:server:run` reads `server/build/android` once `:server:androidRelease` has run.
Desktop client: Compose `packageMsi`. Web client (ADR-029): `:server:webApp` takes the production wasm build (`:apps:web:wasmJsBrowserDistribution`, ~16 MB of wasm, ~6 MB gzipped) and writes a gzip twin of every file; `packageServer` puts it in `web/` beside `lib/`, and the server serves it at `/app/` (gzip when accepted; hash-named files cached for a year, the rest revalidated with Last-Modified, so an update shows on the next reload). `:server:run` serves `server/build/web` once `:server:webApp` has run. In development, `wasmJsBrowserDevelopmentRun` proxies `/api` to a dev server (`BENBOW_DEV_SERVER`, default `https://127.0.0.1:8797`), so the page's origin stands in for the server as it does at `/app/`. `/app/` responses carry a Content-Security-Policy that allows only the server itself (ADR-030); the emoji font (`apps/web` task `emojiFonts`, ~2.9 MB gzipped) ships in `fonts/`.

## Testing strategy
- `shared/core`: unit + property tests (kotest-property): Markdown round-trip, diff3 merge, HLC ordering.
- Sync: deterministic simulation (N clients + server in memory, random ops, drops, duplicates, reorders, crashes). Assert convergence and that no revision is lost.
- Server: Ktor `testApplication` against a temp-dir SQLite. Migration tests against fixture DBs from every schema version. Backup/restore tests.
- UI: Roborazzi screenshot tests (JVM). Desktop smoke via Compose Hot Reload MCP.
- Android performance (6.7): `apps/benchmark` (com.android.test, self-instrumenting) drives `app.benbow.bench`, never the owner's app. `BenchSeedActivity` (benchmark/profiling builds only) fills its empty DB with made-up entries and drawn pictures (`seedYears=N` as an instrumentation argument adds N years of older posts); the benchmarks wait until it is done (before 7.13 they stopped it after 10 s, partway). `StartupBenchmark` (cold, without compilation and with the baseline profile), `FeedBenchmark` (skim, open posts), `BaselineProfileGenerator`. The `benchmark` build is R8 like release; `profiling` is the same without R8, for collecting the profile. Results land in `apps/benchmark/build/outputs/connected_android_test_additional_output/`; Perfetto traces there can be queried with `trace_processor_shell` from benchmark-common, pushed to the phone.
- `./gradlew check` is the single gate.
